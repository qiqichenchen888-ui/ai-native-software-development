# AI Native 软件靠什么思考

前面我们说，AI Native 软件和传统软件最大的区别之一，是：

> **用户不再需要自己决定每一步怎么走，而是把目标交给系统，由 Agent 判断下一步应该做什么。**

但这马上会产生一个新的问题：

> **Agent 凭什么知道下一步应该做什么？**

很多人第一反应可能是：

> 靠大模型。

这句话不能说错，但远远不够。

因为同一个 GPT、Claude，甚至同一个版本的模型，放在不同的软件里，最后表现出来的能力可以完全不一样。

有的只能陪你聊天。

有的可以分析几百份资料。

有的能够连续工作几十分钟，自己找文件、查数据、调用工具，最后交付一份结果。

所以一个 AI Native 软件最终“怎么想”，并不是只由模型决定的。

它至少取决于四样东西：

```text
Model
模型本身有没有判断能力
Context
这一次判断时，它看见了什么
Skill
它知不知道这类事情应该怎么做
Instruction
这一次到底要它做什么，以及基本规则是什么
```

这四样东西放在一起，才比较接近一个 Agent 真正的“思考系统”。

---

## 一、Model：真正需要“判断”的事情，才交给模型

先说最容易理解的 Model。

模型真正有价值的地方，并不是它什么都能做。

而是：

> **它可以处理那些很难提前写成固定规则的问题。**

比如我们现在有一个发稿产品。

用户上传一篇文章，希望系统：

> “帮我推荐 5 家适合这篇文章的媒体。”

如果我们用传统代码做，可能很快就会遇到问题。

因为到底什么叫：

> **“适合”？**

可能需要同时考虑：

- 文章讲的是什么；
- 品牌属于什么行业；
- 这次传播的目的是什么；
- 媒体主要覆盖什么人群；
- 媒体权威性怎么样；
- 用户预算是多少；
- 过去已经发过哪些媒体；
- 媒体价格是否合适；
- 某些媒体虽然行业相关，但内容调性合不合适。

这些东西里面，有很多判断并不是简单的：

```text
如果 A，就 B
如果 C，就 D
```

可以完全写死的。

比如一篇文章同时涉及：

> AI、养老、医疗、企业数字化。

到底应该把它归到科技媒体、养老媒体还是医疗媒体？

可能没有一个绝对答案。

系统必须结合文章内容、传播目标和用户要求去判断。

这种地方才是模型擅长的：

> **处理模糊性。**

所以可以先记住一个很重要的原则：

> **不是所有事情都应该让模型思考。只有那些需要理解、比较、归纳、规划和判断的事情，才值得交给模型。**

---

反过来，有一些东西根本不是“思考题”。

比如：

> 这家媒体现在多少钱？

如果数据库里写的是：

```text
媒体 A
当前价格：800 元
```

模型就不应该在那里分析：

> “根据我的经验，这种媒体大概 600 到 1000 元……”

这时候它越会思考越麻烦。

正确做法就是：

```text
查数据库
↓
800 元
```

再比如：

```text
用户还有多少余额？
订单有没有付款？
文章有没有发布成功？
媒体 ID 是多少？
```

这些都是：

> **事实。**

事实不应该由模型推理出来。

所以 Model 在系统里的位置并不是：

> **“什么都交给 AI。”**

而更接近：

> **确定的事情，让系统直接给答案；不确定的事情，才让模型判断。**

---

## 二、只有模型还不够，它还得知道“现在发生了什么”

假设现在我们真的把推荐媒体这个任务交给一个很强的模型。

你只告诉它一句：

> “帮我推荐 5 家媒体。”

它能不能做好？

大概率不能。

因为它什么都不知道。

它可能马上需要问：

```text
什么文章？
什么品牌？
预算多少？
想达到什么效果？
有哪些媒体可以选择？
媒体现在多少钱？
过去发过哪些？
有没有禁止使用的媒体？
```

所以模型聪不聪明，只是一部分。

还有一个非常重要的问题：

> **它做这一次判断的时候，到底看见了什么？**

这个东西就是：

**Context**

也就是上下文。

---

很多人会把 Context 简单理解成：

> 给 AI 一堆资料。

其实不完全是。

更准确地说：

> **Context 是 Agent 在“这一次判断”时真正需要看到的信息。**

比如现在 Agent 正在做：

> 为这篇文章推荐媒体。

那它此刻可能需要：

```text
用户目标：
推荐 5 家媒体
用户约束：
预算不超过 3000 元
至少一家权威科技媒体
文章：
《企业如何利用 Agent 重构工作流程》
品牌：
一家做企业 AI 服务的公司
历史：
过去 30 天已经发布过 A、B 两家媒体
当前媒体库：
媒体名称
媒体分类
媒体价格
受众
权威等级
当前是否可发布
```

有了这些东西，模型才有可能进行真正有意义的判断。

否则它就只能：

> **猜。**

---

## 三、模型没有一个神秘的“它应该知道”

这一点非常重要。

我们跟 AI 聊天的时候，经常会产生一种错觉：

> “它不是很聪明吗？这个东西它应该知道吧？”

但做真正的软件时，不能这么想。

因为：

> **对于一个具体任务，系统真正能依赖的，不是“模型可能知道什么”，而是这一次运行时我们明确给了它什么。**

例如：

> “这个客户昨天已经批准了发布方案。”

如果这个信息：

- 没进系统；
- 没进当前状态；
- 没放进 Context；

那你不能期待 Agent：

> “自己记得。”

再比如公司内部有一个规则：

> 单笔发布预算超过 5000 元，需要负责人审批。

如果这个规则从来没有提供给 Agent，它也不可能凭空知道你们公司的制度。

所以做 AI Native 软件的时候，我们会逐渐从：

> **“模型知道什么？”**

换成一个更加工程化的问题：

> **“模型在做这个判断时，需要知道什么？”**

这两个问题看起来很像，其实区别非常大。

---

前一种思路容易变成：

> 模型这么聪明，应该没问题。

后一种思路会变成：

```text
它现在要做什么判断？
↓
这个判断需要哪些信息？
↓
这些信息从哪里来？
↓
哪些必须一直提供？
↓
哪些只有需要的时候再读取？
```

这才开始变成真正的软件设计。

---

## 四、Context 也不是越多越好

然后又会出现另外一个很常见的误区：

既然 Context 这么重要，那是不是把所有东西都扔进去就好了？

比如：

```text
整个公司知识库
所有历史聊天记录
所有订单
全部产品资料
全部媒体数据
几十份制度文件
过去三年的运营数据
```

一次性全部给模型。

这样通常也不好。

因为模型真正需要的并不是：

> **信息越多越好。**

而是：

> **此刻需要的信息刚刚好。**

你可以把它理解成一个人在工作。

假如我要你判断：

> “这篇文章适合发哪些媒体？”

我给你：

- 文章；
- 品牌；
- 媒体库；
- 预算；
- 历史发布情况。

这些都有用。

但如果我同时再给你：

- 三年前的员工手册；
- 公司全部报销记录；
- 服务器部署说明；
- 去年的春节放假通知；
- 另外 200 个项目的聊天记录。

这些东西不会让你更聪明。

反而可能：

> **让真正重要的信息被淹没。**

所以 Context Engineering 真正要解决的并不是：

> “怎么把更多东西塞给 AI？”

而是：

> **“这一步到底应该给它什么？”**

---

## 五、但有数据还不够，它还得知道“这类事情应该怎么做”

现在我们假设：

模型很强。

Context 也准备好了。

文章、品牌、预算、媒体数据，全都有了。

这时候 Agent 就一定能推荐好吗？

还是不一定。

因为这里还缺了一个东西：

> **方法。**

比如一个刚入职的新人。

你给他：

```text
一篇文章
完整媒体库
报价
客户预算
历史发布记录
```

然后跟他说：

> “去给客户做一份媒体发布方案。”

他可能还是不知道应该从哪里开始。

为什么？

因为：

> **他有资料，但没有方法。**

---

一个做了五年媒体投放的人，脑子里可能已经有一套自己的方法：

```text
先看文章主题
↓
判断这一次传播目标
↓
判断品牌所在行业
↓
先过滤明显不相关媒体
↓
检查过去发布记录，排除近期重复
↓
按照权威性、相关性、受众匹配排序
↓
结合预算筛选
↓
至少保留一家权威媒体
↓
最后解释每家媒体为什么推荐
```

这套东西不是：

> 这一次任务的数据。

而是：

> **这类工作应该怎么做。**

在 AI Native 软件里，这类专业方法就很适合被做成：

**Skill**

---

## 六、Skill 可以理解成“专家经验说明书”

Skill 最简单的理解就是：

> **把一个专家脑子里“这种事情应该怎么做”的方法，变成 Agent 可以使用的能力。**

比如：

```text
媒体推荐 Skill
```

里面可能规定：

**什么时候使用**

当用户要求：

> 根据文章推荐媒体、制定发布方案。

---

**需要哪些输入**

```text
文章
品牌信息
传播目标
预算
媒体库
历史发布记录
```

---

**应该怎么做**

```text
1. 分析文章主题
2. 判断目标用户
3. 过滤不相关媒体
4. 排除近期重复媒体
5. 综合行业相关性、权威性、价格排序
6. 检查预算
7. 生成推荐理由
```

---

**最后应该产出什么**

例如：

```text
媒体名称
媒体类型
价格
推荐理由
匹配度
总预算
风险提示
```

这就是一个比较完整的 Skill。

---

所以 Skill 和 Context 的区别就非常清楚了。

比如：

> **Context 告诉 Agent：“这次是什么情况。”**

而：

> **Skill 告诉 Agent：“这种情况通常应该怎么办。”**

可以记成：

```text
Context
= 这一次任务的材料
Skill
= 这一类任务的方法
```

这个区别非常重要。

---

## 七、Skill 也不应该全部塞进一个巨大 Prompt

以前做 AI 应用，很容易采用一种方式：

> 把所有东西全写进 Prompt。

例如：

```text
你是一个高级媒体专家……
遇到企业客户应该……
如果是 AI 行业应该……
如果预算不足应该……
推荐媒体的时候先……
然后……
注意……
另外……
```

最后 Prompt 越写越长。

几千字、几万字。

什么都在里面：

```text
角色
业务规则
专业方法
输出格式
案例
知识
限制
流程
```

刚开始可能还能用。

后面一定越来越难维护。

因为你根本不知道：

> 改了一条规则，到底影响了什么？

更好的方式，是把不同的东西拆开。

比如：

```text
Instruction
→ 这次 Agent 是谁、目标是什么
Context
→ 当前任务需要知道什么
Skill
→ 这类工作应该怎么做
Tool
→ 下一章再讲，具体怎么真的去行动
```

这样能力才可以单独调整。

比如有一天发现：

> 媒体推荐方法不够好了。

那就修改：

```text
媒体推荐 Skill
```

而不是把整个 Agent 的所有提示词重新改一遍。

---

## 八、Instruction：告诉它“你现在到底在干什么”

除了 Model、Context 和 Skill，还有一个很容易被忽略的东西：

**Instruction**

可以简单理解成：

> **Agent 当前这份工作的基本说明。**

比如：

```text
你的任务：
根据用户提供的文章和品牌信息生成媒体发布方案。
你的责任：
负责分析与推荐，不负责最终付款。
你的基本要求：
价格必须来自当前媒体数据库；
不能虚构媒体；
预算不得超过用户限制；
如果信息不足，需要明确指出；
最终输出发布方案。
```

它更像：

> **工作岗位说明 + 当前任务说明。**

---

所以这几个东西其实承担的是不同角色。

```text
Model
我有没有判断能力？
Instruction
我现在到底要做什么？
Context
这一次到底是什么情况？
Skill
这类事情专业上应该怎么做？
```

四个东西一起工作。

---

## 九、用一个完整例子看，它到底是怎么“想”的

还是拿我们的发稿产品举例。

用户说：

> “帮我给这篇关于企业 Agent 的文章推荐 5 家媒体，预算 3000 元以内，希望专业一点。”

如果只是一个普通模型，它可能直接根据自己的知识开始推荐：

```text
36氪
虎嗅
钛媒体
……
```

问题马上就来了：

> 这些媒体我们真的有资源吗？
> 
> 当前价格是多少？
> 
> 现在还能不能发？
> 
> 用户以前发没发过？
> 
> 3000 元够不够？

模型不知道。

---

而一个真正的软件系统会先准备这一次判断需要的东西。

**Instruction**

```text
目标：
生成一份真实可执行的媒体发布方案。
要求：
只能使用当前媒体库中的媒体；
价格必须使用当前报价；
总预算 ≤ 3000；
不得推荐过去 30 天已经发布过的媒体。
```

**Context**

```text
文章：
企业 Agent 相关内容
品牌：
企业 AI 服务公司
预算：
3000
历史：
最近发布过媒体 A、B
当前媒体库：
……
```

**Skill**

```text
按照：
行业相关性
→ 受众匹配
→ 权威性
→ 历史效果
→ 价格
进行筛选和排序。
```

**Model**

最后才负责：

> **在这些信息和方法之上进行判断。**

于是它可能得到：

```text
媒体 1
高度相关、企业科技受众为主
800 元
媒体 2
行业相关性稍低，但权威性较高
1000 元
媒体 3
……
```

这时候你会发现：

> 模型其实只是整个“思考系统”里面的一部分。

真正让它做出一个靠谱判断的，是：

```text
模型能力
+
正确任务
+
正确材料
+
正确方法
```

缺一个，结果都可能完全不一样。

---

**十、所以不要再问“这个模型聪不聪明”**

以后我们做 AI Native 软件，再遇到 Agent 做错事情的时候，第一反应不应该永远是：

> “是不是模型不够强？”

当然，有时候确实是模型能力的问题。

但更多时候应该拆开来看：

```text
是 Model 不会判断？
还是 Context 没给够？
还是给了错误的 Context？
还是 Skill 本身的方法就有问题？
还是 Instruction 根本没有把目标说清楚？
```

比如 Agent 推荐错了媒体。

以前我们可能会：

> 换一个更大的模型。

但真正排查以后可能发现：

> 当前媒体报价根本没有给 Agent。

或者：

> Skill 里面根本没有“排除最近发布媒体”这个步骤。

或者：

> 用户虽然说了预算 3000，但系统压根没有把这个约束放进当前任务。

这时候换再强的模型也没有用。

---

**十一、AI Native 软件的“思考”，其实是一套被组织起来的判断过程**

**所以回到这一章最开始的问题**：

> **AI Native 软件到底靠什么思考？**

答案并不是简单的：

> 靠大模型。

而是：

```text
Model
提供理解、推理和判断能力
+
Instruction
告诉它当前目标和基本规则
+
Context
提供这一次任务真正需要的信息
+
Skill
提供这类专业工作的方法
```

如果一定要压缩成一句话，可以理解成：

> **模型负责想，Context 决定它看见什么，Skill 决定它会不会做，Instruction 决定它现在应该做什么。**

但到这里，我们解决的仍然只是：

> **Agent 怎么知道下一步应该干什么。**

知道应该干什么，不代表它真的能干。

一个模型可能非常清楚地告诉你：

> “下一步应该查询媒体数据库，然后读取最新报价。”

但如果它只能坐在聊天框里跟你说：

> “你现在可以打开媒体后台查询一下。”

那么真正干活的人还是你。

所以接下来真正的问题就变成了：

> **怎么让 AI 不只是会想，而是真的可以在软件里做事情？**

这就进入下一章：

**AI Native 软件到底怎么做事**

这一章会开始讲清楚 **Tool、Workflow、Harness、Agent Loop 和 Environment** 之间到底是什么关系，以及为什么“能调用一个 API”还远远不等于真正的 Agent。
