# 怎么保证 AI Native 系统不失忆

前面我们已经解决了两个问题。

第一，AI Native 软件靠什么思考：

```text
Model
+ Instruction
+ Context
+ Skill
```

第二，它怎么真正做事：

```text
Agent
+ Tool
+ Workflow
+ Harness
+ Environment
```

到这里，一个 Agent 已经可以：

> 理解目标、判断下一步、调用工具、观察结果，然后继续工作。

但只要任务稍微变长一点，马上就会碰到一个特别现实的问题：

> **它能不能记得自己做到哪里了？**

比如用户让我们的发稿系统：

> “帮我给这篇文章制定发布方案，我确认以后直接下单。”

Agent 已经做到：

```text
分析文章 ✅
筛选媒体 ✅
生成方案 ✅
用户确认 ✅
创建订单 ✅
等待供应商返回结果……
```

结果这个时候：

> 页面刷新了。

或者：

> 网络断了。

或者：

> 服务重启了。

或者任务太长，原来的 Context 已经装不下，需要换一个新的会话继续。

如果重新打开以后，Agent 对你说：

> “您好，请问有什么可以帮您？”

那这个系统其实还没有真正具备持续工作的能力。

因为一个真正的 AI Native 系统不能只是：

> **这一轮很聪明。**

它还必须做到：

> **下一轮准确知道上一轮发生过什么。**

---

## 一、聊天记录不是“记忆系统”

很多 AI 产品最开始都会有一个很自然的想法：

> 我把聊天记录存下来不就行了吗？

比如昨天用户说：

> “这五家媒体我确认了，可以发布。”

今天把这段聊天重新塞给模型。

模型看到以后：

> “哦，用户已经确认了。”

听起来好像没问题。

但真正做软件以后，这种方式很危险。

因为聊天记录是一段：

> **自然语言。**

而业务状态需要的是：

> **确定事实。**

比如一句：

> “可以，就这样吧。”

到底代表什么？

可能是：

```text
确认推荐方案？
确认报价？
确认下单？
确认发布？
只是觉得方案还不错？
```

人结合上下文可能知道。

但正式系统不能靠猜。

---

再比如聊天记录里写着：

> “订单已经创建成功。”

这句话是谁说的？

是：

- 模型自己生成的？
- Tool 返回的？
- 数据库真的写成功了？
- 用户以为成功了？
- 第三方供应商返回成功了？

这几种情况完全不是一回事。

所以有一个特别重要的原则：

> **聊天可以记录交流，但不能充当业务事实的唯一来源。**

真正影响业务的事情，必须被保存成结构化、可以查询的状态。

---

## 二、真正要解决“失忆”，靠的是 State

这个东西就是：

**State**

State 可以简单理解成：

> **系统现在到底处于什么状态。**

例如一项发布任务。

不是让模型自己回忆：

> “我记得好像已经推荐完了。”

而是系统里明确存着：

```text
run_id: publish_20260914_001
current_stage:
WAITING_SUPPLIER
plan_status:
APPROVED
order_id:
OUR-1001
selected_media:
[138, 256, 301, 412, 520]
completed_actions:
- article_analyzed
- media_selected
- plan_created
- user_approved
- order_created
last_error:
null
```

这样即使：

> 换了一个模型。

甚至：

> 原来的对话全部消失了。

新的 Agent 只要重新读取 State，就知道：

> 这个任务不是刚刚开始。

而是：

> **已经下单，现在正在等供应商。**

这才叫真正的可恢复。

---

所以 State 和聊天记录最大的区别在于：

聊天记录是：

> **“大家之前说过什么。”**

State 是：

> **“现实里现在到底是什么情况。”**

这两个东西千万不能混在一起。

---

## 三、State 不是为了让 AI“记性更好”

这点我觉得特别值得单独说。

我们平时会觉得：

> AI 容易失忆，所以给它 Memory。

但在真正的软件里，解决业务任务的持续性，并不是想办法让模型：

> “记得更多。”

而是应该反过来：

> **重要的事情根本不要让模型负责记。**

比如：

```text
订单有没有创建？
用户有没有批准？
文章有没有发布？
退款有没有发生？
当前报告是第几个版本？
任务执行到哪个阶段？
```

这些都不应该成为：

> 模型记忆。

而应该成为：

> **系统事实。**

这其实很像人和公司的关系。

你作为员工可能会忘记：

> 昨天这个客户聊到哪了。

没关系。

打开 CRM。

里面写着：

```text
客户阶段：
合同审批中
```

你马上就能继续。

真正成熟的软件，本来就不应该依赖某个人脑子里的记忆。

Agent 也是一样。

> **我们不是要造一个永远不会忘记的 AI，而是要造一个即使 AI 忘了，也能准确恢复工作的系统。**

---

## 四、Memory 和 State 完全不是一个东西

说到这里，就可以把一个特别容易混淆的概念拆开：

**Memory**

Memory 也确实是“记忆”。

但它和 State 记的东西完全不一样。

比如用户以前说：

> “我不喜欢特别长的报告。”

系统可以记住：

```text
用户偏好：
报告尽量简洁
```

或者：

> “以后推荐媒体的时候，我更喜欢权威媒体。”

这些都可以成为 Memory。

因为它们是：

> **对以后任务有帮助的偏好和经验。**

但是：

```text
用户已经批准方案
订单已经创建
已经扣除 3000 元
供应商已经发布
```

这些绝对不能只是 Memory。

因为它们是：

> **必须百分之百准确的业务事实。**

所以可以记一个特别简单的区别：

> **Memory 是“最好记得”。**
> 
> **State 是“绝对不能记错”。**

这个区别非常重要。State 用来保存系统必须准确恢复的事实，而 Memory 更像跨任务可复用的偏好和经验。

---

比如：

```text
用户喜欢：
简洁一点
```

Memory 忘了。

最多就是：

> 报告这次写长了一点。

但如果系统忘了：

```text
这笔钱已经付过了
```

然后又付一次。

这就不是：

> “AI 体验不好。”

而是：

> **生产事故。**

---

## 五、State 还要回答一个问题：现在做到哪一步了？

长任务还有一个特别重要的问题：

> **阶段。**

例如一个发稿任务不是简单的：

```text
未完成
/
已完成
```

中间其实会经历很多阶段：

```text
CREATED
↓
ANALYZING
↓
PLAN_DRAFTED
↓
WAITING_APPROVAL
↓
APPROVED
↓
ORDER_CREATED
↓
PUBLISHING
↓
PUBLISHED
↓
COMPLETED
```

这些阶段最好明确存在系统里。

因为不同阶段：

> **允许做的事情是不一样的。**

例如：

```text
WAITING_APPROVAL
可以：
查看方案
修改方案
批准方案
不可以：
直接正式下单
```

到了：

```text
APPROVED
```

才允许：

```text
创建订单
```

到了：

```text
ORDER_CREATED
```

就不应该再次：

```text
创建同一张订单
```

所以 State 不只是：

> 帮 Agent 记忆。

它还在告诉整个系统：

> **现在处于什么阶段，以及接下来哪些动作才是合法的。**

---

## 六、不要让模型自己宣布“状态已经变了”

这个问题也特别关键。

假设 Agent 调用了：

```text
create_order()
```

然后模型说：

> “订单创建成功。”

是不是订单就真的创建成功了？

当然不是。

真正的顺序应该是：

```text
Agent：
我要创建订单
↓
Tool：
执行 create_order()
↓
业务系统：
检查条件
写入数据库
↓
数据库：
order_id = OUR-1001
status = CREATED
↓
系统返回真实状态
↓
Agent：
订单已创建
```

也就是说：

> **模型可以提出“我要改变状态”，但真正的状态变化必须由系统完成。**

不能是：

```text
模型：
我已经把订单状态修改为成功。
```

然后前端就：

```text
status = SUCCESS
```

这非常危险。

---

所以这里有一个特别重要的分工：

> **模型负责提出动作。**
> 
> **代码负责确认事实。**

比如：

```text
模型判断：
应该创建订单
代码判断：
现在允不允许创建订单
Tool：
执行创建
数据库：
保存真实结果
State：
记录当前状态
```

模型不能自己给自己颁发：

> “成功证书。”

正式状态必须由领域代码验证并写进权威存储，再把真实结果返回给 Agent。

---

## 七、Artifact：工作成果也不能只留在聊天里

除了 State，还有另外一种东西也很容易被我们忘掉：

> **Agent 已经做出来的成果怎么办？**

比如 Agent 花了十分钟：

> 做出了一份媒体发布方案。

如果这份东西只是存在聊天里：

```text
Assistant:
根据您的文章，我建议……
```

然后过两天用户又说：

> “就在上次那一版基础上，把预算改成 5000。”

系统就开始麻烦了。

到底：

> 上次哪一版？
> 
> 有没有人修改过？
> 
> 用户最后确认的是哪一版？
> 
> 当时价格是多少？
> 
> 当前这份和批准的版本一样吗？

所以复杂任务的成果不应该只是：

> **聊天文本。**

而应该形成一个独立对象：

**Artifact**

比如：

```text
publish_plan_id:
PLAN-001
version:
3
status:
APPROVED
budget:
2950
media:
[...]
created_at:
...
approved_at:
...
```

这份发布方案就是一个 Artifact。

---

Artifact 可以理解成：

> **Agent 真正留下来的工作成果。**

例如：

- 一份报告；
- 一张表；
- 一个发布方案；
- 一份合同草稿；
- 一个代码修改；
- 一份调研结果；
- 一个申请单。

这些东西应该：

```text
有 ID
有版本
有状态
有来源
可以修改
可以比较
可以继续使用
```

而不是：

> 永远埋在聊天记录里面。

复杂任务的成果本来就应该成为可保存、可审阅、可修改、可版本化的独立对象。

---

## 八、State 和 Artifact 到底有什么区别？

这两个东西很容易混。

还是拿发布任务举例。

State 更像：

> **任务现在进行到哪里。**

比如：

```text
当前阶段：
WAITING_APPROVAL
用户是否批准：
false
订单是否创建：
false
```

Artifact 则是：

> **这项工作目前产出了什么。**

例如：

```text
发布方案 V3
```

里面包含：

```text
媒体 A
媒体 B
媒体 C
媒体 D
媒体 E
总预算 2950
推荐理由……
```

所以可以简单记成：

```text
State
= 任务进度和事实
Artifact
= 工作成果
```

例如写文章也是一样。

State：

```text
当前：
正在写第二章
```

Artifact：

```text
AI Native 软件文章 V7
```

它们是两类不同的东西。

---

## 九、Checkpoint：长任务必须有“存档点”

有了 State 和 Artifact 以后，还有一个东西特别适合长任务：

**Checkpoint**

Checkpoint 可以理解成：

> **游戏存档。**

假设一个任务要运行一个小时。

如果只有：

```text
开始
↓
……
↓
完成
```

中间任何地方挂掉，都从头开始。

那就非常痛苦。

更合理的是：

```text
完成资料收集
↓
Checkpoint 1
完成初步分析
↓
Checkpoint 2
形成草稿
↓
Checkpoint 3
等待用户批准
↓
Checkpoint 4
执行正式动作
```

这样如果 Agent 在：

> 形成草稿以后挂了。

下一次不用再：

```text
重新搜资料
重新分析
重新生成
```

而是：

> **从最近一个可靠阶段继续。**

---

比如我们的发布任务：

```text
文章分析完成 ✅
        ↓
Checkpoint
候选媒体筛选完成 ✅
        ↓
Checkpoint
发布方案完成 ✅
        ↓
Checkpoint
用户批准 ✅
        ↓
Checkpoint
创建订单
```

为什么：

> 用户批准以后

特别适合有一个 Checkpoint？

因为这是一个重要边界。

下一次恢复时，系统必须知道：

> **这个方案已经被用户批准过。**

不应该又回到：

> “请问您是否确认？”

也不能更糟糕：

> 忘记之前批准的是哪个版本。

---

## 十、Checkpoint 和 State 也不是一回事

这两个也可以简单区分。

State 是：

> **持续变化的当前状态。**

Checkpoint 是：

> **一个可以安全恢复的位置。**

比如：

```text
State：
当前正在执行第 7 步
搜索到了 18 家媒体
其中 9 家已经完成价格检查
```

这是实时变化的。

而：

```text
Checkpoint：
媒体初筛阶段已完成
方案草稿 V1 已保存
```

是：

> 一个稳定存档点。

有点像打游戏：

State 是：

> 你现在血量 72，正在和 Boss 打。

Checkpoint 是：

> Boss 房间门口那个存档。

---

## 十一、为什么长任务不能全部依赖 Context

还有一个很现实的问题。

模型是有 Context Window 的。

即使未来越来越大，也不代表：

> 一项任务从头到尾的所有内容都应该永远塞进去。

比如一个 Agent 工作几个小时。

中间可能产生：

```text
几百次 Tool 调用
大量日志
几十份资料
多个版本的 Artifact
很多失败信息
用户多次修改
```

你不可能永远把所有东西全部放进模型 Context。

所以一个长期工作的 Agent 必须逐渐做到：

> **把“记忆”外部化。**

也就是说：

```text
现在做到哪
→ State
已经形成什么成果
→ Artifact
哪些阶段完成
→ Checkpoint
用户长期偏好
→ Memory
这一次判断需要什么
→ 再从这些地方组织成 Context
```

这里其实出现了一个非常重要的关系：

```text
State / Memory / Artifact
不是 Context 本身
↓
而是 Context 的来源之一
```

每一次模型真正需要思考的时候，Harness 再从系统里面把：

> **这一步需要的信息**

重新拿出来，组成新的 Context。

而不是要求模型：

> “你千万别忘。”

这也是长任务能够跨会话、跨 Context Window 持续工作的关键。

---

## 十二、换一个模型，也应该还能继续工作

这个标准我觉得特别适合判断一个 AI Native 系统有没有真的解决“失忆”。

假设今天任务跑到一半。

原来使用的是：

```text
Model A
```

明天我们升级了模型：

```text
Model B
```

新的模型一进来。

它能不能通过系统里的：

```text
Goal
State
Artifact
Checkpoint
规则
证据
```

准确知道：

> **现在是什么任务、已经发生了什么、下一步应该做什么。**

如果可以，那说明：

> **进度真正属于系统。**

如果不可以，必须依赖：

> “原来的那个聊天线程不能丢。”

那说明大量关键状态仍然偷偷藏在：

> **模型 Context 里面。**

这种系统长期一定会遇到问题。

---

## 十三、页面也不能成为唯一的 State

还有一种很常见的问题。

有些系统会把状态放在：

> 浏览器前端。

比如用户打开页面时：

```text
currentStep = 4
```

界面显示：

> 正在发布。

但一刷新页面：

```text
currentStep = 1
```

完了。

这是因为：

> **页面记住了状态，系统没有。**

真正重要的 State 应该在服务端有一个权威版本。

前端只是：

> **读取它，然后显示出来。**

所以：

```text
数据库 / 服务端 State
= 真相
UI
= 真相的展示
```

而不是：

```text
UI 显示什么
= 系统现在就是什么
```

这也是为什么真正的长任务运行时，UI 更像 Harness 的一个客户端；真正的 Run、事件和进度应该拥有自己的持久状态。

---

## 十四、我们用一个完整任务看它怎么“不失忆”

还是回到我们的发稿产品。

用户说：

> “帮我制定一个 3000 元的发布方案，确认以后直接发。”

系统首先创建：

```text
run_id:
RUN-001
```

State：

```text
stage:
ANALYZING
user_approved:
false
order_id:
null
```

然后 Agent 开始工作。

---

### 第一步：完成文章分析

State 更新：

```text
stage:
SELECTING_MEDIA
```

保存当前分析结果。

Checkpoint：

```text
ARTICLE_ANALYSIS_COMPLETED
```

---

### 第二步：生成发布方案

创建 Artifact：

```text
PLAN-001
version: 1
status: DRAFT
```

State：

```text
stage:
WAITING_APPROVAL
artifact_id:
PLAN-001
```

然后页面关闭了。

---

第二天用户重新打开。

系统不需要问：

> “昨天我们聊到哪里？”

直接读取：

```text
RUN-001
```

看到：

```text
stage = WAITING_APPROVAL
artifact_id = PLAN-001
```

于是界面直接显示：

> “昨天的发布方案正在等待您确认。”

用户点击：

> 确认。

系统更新：

```text
PLAN-001
status = APPROVED
State:
user_approved = true
stage = READY_TO_ORDER
```

留下 Checkpoint。

---

接下来创建订单：

```text
order_id:
OUR-1001
```

State：

```text
stage:
WAITING_SUPPLIER
```

结果服务重启。

---

重新启动以后：

Agent 读取：

```text
RUN-001
stage:
WAITING_SUPPLIER
order_id:
OUR-1001
```

它就知道：

> **不能重新创建订单。**

应该继续：

> 查询 `OUR-1001` 的供应商执行状态。

这才是真正的：

> **续上。**

不是：

> “模型好像记得。”

而是：

> **系统知道。**

---

## 十五、所以一个不失忆的 AI Native 系统，到底需要什么？

现在就可以把这一章压缩一下。

它至少需要四类东西。

### State

回答：

> **现在到底是什么情况？**

例如：

```text
做到哪个阶段
哪些动作已经发生
当前状态是什么
```

---

### Memory

回答：

> **过去有什么经验或偏好，对以后可能有帮助？**

例如：

```text
用户喜欢简洁报告
用户偏好权威媒体
```

---

### Artifact

回答：

> **到目前为止，真正产生了什么工作成果？**

例如：

```text
发布方案
报告
表格
草稿
代码
```

---

### Checkpoint

回答：

> **如果现在中断，可以从哪里安全继续？**

例如：

```text
资料收集完成
方案完成
人工批准完成
```

四个东西放在一起：

```text
Memory
记经验
State
记事实
Artifact
留成果
Checkpoint
留存档
```

这时候 Agent 才开始从：

> **一次性的 AI 对话**

变成：

> **一个可以持续推进工作的系统。**

---

## 十六、真正的“不失忆”，不是让模型记住一切

所以回到这一章最开始的问题：

> **怎么保证 AI Native 系统不失忆？**

答案并不是：

> 给模型更大的上下文。

也不是：

> 把所有聊天记录永久保存。

更不是：

> 在 Prompt 里告诉它“请记住之前发生的一切”。

真正的方法是：

> **把必须准确的事情从模型脑子里拿出来，变成系统可以持久保存和重新读取的对象。**

也就是：

```text
业务事实
→ State
用户长期偏好
→ Memory
工作成果
→ Artifact
可恢复节点
→ Checkpoint
```

模型可以忘。

会话可以结束。

Context 可以重新构建。

甚至模型本身都可以更换。

只要这些东西还在：

> **工作就应该可以继续。**

---

但是做到这里以后，我们又会遇到一个更麻烦的问题。

现在的 Agent：

```text
不会失忆了
会调用 Tool
会修改 State
还能跨会话继续工作
```

这意味着：

> **它真的越来越能干了。**

但 Agent 越能干，一个问题就越危险：

> **如果它判断错了怎么办？**

比如它认为：

> “为了完成任务，我应该直接下单。”

或者：

> “这个文件应该删掉。”

或者：

> “用户大概同意了，直接发布吧。”

一个只能聊天的 AI 说错一句话，可能只是答案不好。

一个拥有 Tool、权限和持久状态的 Agent 如果做错，是真的可能：

> **改变现实世界。**

所以接下来我们必须解决另外一个问题：

**怎么保证 AI Native 系统不乱来**

这一章会真正进入 **Authority、Permission、Guardrail、Sandbox 和 Human Gate**：

到底什么事情可以交给 Agent 自己决定，什么事情必须由代码拦住，什么事情一定要停下来让人批准，以及为什么“在 Prompt 里告诉 AI 不要乱来”远远不够。
