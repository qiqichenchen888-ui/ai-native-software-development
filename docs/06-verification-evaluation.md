# 怎么知道 AI Native 系统真的完成了

前面几章，我们已经让一个 AI Native 系统越来越像一个真正能工作的系统了。

它现在已经可以：

```text
理解目标
↓
根据 Context 和 Skill 判断下一步
↓
调用 Tool 做事
↓
把进度保存进 State
↓
中断之后继续
↓
在 Permission、Guardrail 和 Human Gate 的边界里行动
```

看起来好像已经差不多了。

但真正到了生产环境，还剩下一个特别关键的问题：

> **它说自己做完了，凭什么相信它？**

这个问题其实比“它会不会做”还重要。

因为模型有一个很明显的特点：

> **它非常擅长生成一个“看起来像完成了”的答案。**

比如你让 Agent：

> “帮我把这篇文章发布到 5 家媒体。”

过了一会儿它告诉你：

> “任务已完成，文章已经成功发布至 5 家媒体。”

听起来很好。

但真实情况可能是：

```text
媒体 A：成功
媒体 B：成功
媒体 C：供应商已接单，但还没有发布
媒体 D：发布失败
媒体 E：Agent 根本没有调用
```

可模型根据当前看到的信息，依然有可能总结成：

> “发布任务已完成。”

这时候问题就不是 AI 会不会说话了。

而是：

> **我们到底依据什么判断一项任务已经 Done？**

---

## 一、传统软件里的“完成”其实很简单

为什么过去的软件没有那么强调这个问题？

因为传统软件的流程通常是写死的。

例如一个上传功能：

```text
用户选择文件
↓
上传
↓
服务端保存
↓
数据库写入成功
↓
返回 SUCCESS
```

什么叫完成？

程序员提前写好了：

```text
数据库写成功
= 完成
```

再比如转账：

```text
验证账户
↓
校验余额
↓
执行交易
↓
账本落账
↓
返回交易状态
```

系统知道：

> 哪一步算成功，哪一步算失败。

因为路径和结果都比较确定。

---

但 Agent 不一样。

比如：

> “帮我分析这个月销售为什么下降，并给出三个最应该优先解决的问题。”

这里没有一个简单的：

```text
if xxx == true:
    done
```

因为系统可能需要：

```text
查销售
查客户
查产品
分析地区
找异常
比较历史
形成原因
提出建议
```

甚至每一次执行的路径都可能不同。

所以当软件从：

> **执行固定功能**

变成：

> **完成开放目标**

我们就必须重新定义：

> **到底怎样才算做完？**

---

## 二、所以 Goal 不能只有一句“我要什么”

我们前面一直在讲：

> AI Native 软件应该从 Goal 开始。

比如：

> “给这篇文章做一个媒体发布方案。”

但如果 Goal 只有这一句话，其实还不够。

因为：

> 什么叫“做好了一个发布方案”？

Agent 可能给你：

```text
建议发布科技媒体、财经媒体和综合媒体。
```

它也可以说：

> 我已经给方案了。

你可能却认为：

> 这算什么方案？

所以 Goal 后面必须跟着一个非常重要的东西：

**Done Criteria**

也就是：

> **满足什么条件，才允许系统说“完成”。**

例如我们的发布方案：

```text
Goal：
给这篇文章制定一份
3000 元以内的媒体发布方案。
```

可以进一步定义：

```text
Done Criteria：
1. 至少推荐 5 家媒体
2. 所有媒体必须真实存在于当前媒体库
3. 总预算 ≤ 3000 元
4. 至少包含 1 家权威媒体
5. 不能推荐过去 30 天已经发布过的媒体
6. 每家媒体必须有推荐理由
7. 价格必须来自当前数据库
```

到这里，“完成”第一次变得：

> **可以检查。**

---

所以一个目标最好不是：

```text
我要一个发布方案。
```

而是：

```text
我要一个发布方案。
而且：
A 必须满足
B 必须满足
C 必须满足
D 不能发生
```

这才真正成为一个可以交给 Agent 执行的目标契约。复杂任务在开始前就应该明确目标、输入、完成标准、证据要求、约束以及需要人工决定的事项。

---

## 三、Done Criteria 一定要在开始之前写

这个顺序特别重要。

不能等 Agent 做完以后，再看结果问：

> “嗯……这样算完成吗？”

因为这样验收标准会一直飘。

比如 Agent 先推荐了 3 家媒体。

你觉得少了：

> “至少得有 5 家吧。”

Agent 又补到 5 家。

然后你发现：

> “怎么超预算了？”

再加：

> 不能超过 3000。

然后又发现全是普通媒体：

> “至少应该有一家权威媒体。”

这样系统永远不知道：

> 到底什么时候才能停。

---

真正合理的方式应该是：

```text
开始任务之前
Goal
↓
Constraints
↓
Done Criteria
↓
Evidence Required
全部先定义
然后再运行 Agent
```

这件事看起来好像只是产品需求写得更清楚。

实际上它还有一个非常大的价值：

> **它给 Agent 一个停止条件。**

否则 Agent 很容易出现两个极端。

一种是：

> 做了一点就觉得完成了。

另一种是：

> 一直优化，永远不知道什么时候该停。

所以 Done Criteria 不只是：

> 用户验收用。

也是 Agent Runtime 判断：

> **什么时候应该 Stop**

的重要依据。

---

## 四、但是“符合条件”不能靠模型自己判断

现在我们已经有了：

```text
Goal
+
Done Criteria
```

是不是就够了？

还不够。

因为如果最后还是让 Agent 自己问自己：

> “我有没有满足 Done Criteria？”

问题依然存在。

比如要求：

```text
至少 5 家媒体
总预算 ≤ 3000
```

模型完全有能力检查。

但我们为什么还要专门设计其他机制？

因为这里有一个非常重要的问题：

> **做事的人，不应该成为唯一的验收人。**

---

这就像一个开发者修完 Bug 以后说：

> “我检查过了，肯定没问题。”

当然有参考价值。

但真正的软件工程不会只靠：

> 开发者自己觉得 OK。

而是会运行：

```text
单元测试
集成测试
自动化测试
代码检查
人工验收
```

原因很简单：

> **生成结果的人，天然不适合成为结果的唯一裁判。**

Agent 也是一样。

---

比如 Coding Agent 修改了一个 Bug。

它看了一眼自己的代码：

> “逻辑没问题，Bug 已修复。”

这不叫证明。

真正有意义的是：

```text
原来的失败测试
↓
现在通过
相关回归测试
↓
通过
程序可以启动
↓
通过
```

这些才是：

> **来自环境的证据。**

---

## 五、Verifier：专门负责回答“这一单到底过没过”

这个东西就叫：

**Verifier**

可以理解成：

> **验收员。**

Agent负责：

> 做事情。

Verifier负责：

> **检查事情到底有没有按要求做完。**

---

还是刚才的发布方案。

Done Criteria 是：

```text
至少推荐 5 家
预算 ≤ 3000
至少一家权威媒体
不能有重复媒体
媒体必须存在
价格必须来自当前数据库
```

那么 Verifier 就可以检查：

```text
推荐数量 == 5？
✅
total_price <= 3000？
✅
authority_media_count >= 1？
✅
duplicate_count == 0？
✅
所有 media_id 都存在？
✅
报价与当前数据库一致？
✅
```

全部通过以后：

```text
VERIFIED
```

这时候系统才有资格说：

> **这个方案满足了我们定义的完成条件。**

Verifier本质上就是用于证明某个里程碑或最终结果是否满足条件的测试、脚本、评测器或者 Readback。

---

## 六、Verifier 最重要的地方，是尽量独立于 Agent

这个“独立”很重要。

比如 Agent 自己生成：

```text
媒体 A
价格：800
```

然后 Agent 又自己说：

> “我确认媒体 A 的价格是 800。”

这不叫验证。

只是：

> 自己重复了一遍自己刚才的答案。

---

更好的方式应该是：

```text
Agent 结果：
媒体 A = ¥800
↓
Verifier 去权威数据库查询：
get_media_price(A)
↓
真实结果：
¥800
↓
一致
✅
```

这样才叫：

> **独立反馈。**

---

同样：

Agent说：

> “文章已经发布成功。”

Verifier不能问 Agent：

> “你确定吗？”

而应该去查：

```text
订单状态
供应商状态
发布 URL
页面是否可访问
```

最后拿真实证据回来。

所以一个很重要的原则是：

> **Verifier 尽量不要验证“Agent 说了什么”，而应该验证“现实世界现在到底是什么”。**

---

## 七、不是所有东西都能用一个 if 判断

但是这里又会遇到一个问题。

有些 Done Criteria 非常确定。

例如：

```text
数量 ≥ 5
预算 ≤ 3000
媒体必须存在
订单状态 == PUBLISHED
```

这种特别适合程序验证。

但有些东西没那么确定。

比如：

> “推荐理由要合理。”
> 
> “方案要专业。”
> 
> “文章质量要达到可发布水平。”
> 
> “分析有没有真正抓住核心问题。”

这些东西很难写成：

```text
if professional == true:
```

那怎么办？

---

这时候验证方式其实可以分层。

### 第一类：代码可以直接验证的

比如：

```text
数量
金额
格式
ID 是否存在
状态
是否重复
字段完整性
权限
```

尽量交给代码。

---

### 第二类：需要规则或计算验证的

比如：

```text
是否至少覆盖 3 个媒体类型
引用与来源是否一致
预算分配是否符合策略
结果是否与数据库数据一致
```

可以用专门脚本或规则检查。

---

### 第三类：确实需要判断的质量问题

例如：

> 推荐理由到底好不好？
> 
> 一篇报告到底有没有回答用户核心问题？

这种时候可能仍然需要：

```text
模型评分
专家评分
人工验收
```

但是即使使用模型来评判，也最好：

> **把标准提前定义出来。**

比如不是问：

> “这个方案好吗？”

而是拆成：

```text
行业相关性
是否有事实依据
推荐理由是否对应具体媒体
是否考虑用户目标
是否存在明显矛盾
```

这样评价才不会完全凭感觉。

---

## 八、Evidence：不仅要告诉用户“完成了”，还要告诉他凭什么

还有一个特别重要的概念：

**Evidence**

也就是：

> **完成证据。**

比如系统显示：

> “5 家媒体已经全部发布完成。”

用户最好能继续看到：

```text
媒体 A
状态：已发布
链接：https://...
发布时间：...
媒体 B
状态：已发布
链接：https://...
发布时间：...
```

而不是只有一个绿色：

```text
✅ 已完成
```

---

同样，一个研究 Agent 告诉用户：

> “数据显示方案 A 的效果更好。”

应该尽量能继续回答：

> 数据来自哪里？
> 
> 哪些数据支持这个判断？
> 
> 哪些地方存在不确定性？

---

所以好的 AI Native 软件最后交付的不只是：

> **结论。**

而应该是：

```text
结论
+
证据
+
来源
+
当前状态
```

这也是为什么 Artifact 很重要。

一个真正的 Artifact 不只是最终文字，它最好能保留来源、版本、状态、生成过程中的关键证据，并且能被审阅和继续使用。

---

## 九、Verifier 和 Artifact 其实经常会连在一起

比如 Agent 生成一份：

```text
发布方案 PLAN-001
```

这个 Artifact 刚生成的时候可能是：

```text
status = DRAFT
```

Verifier开始检查。

如果：

```text
数量不足
预算超出
有媒体不存在
```

那么：

```text
verification = FAILED
```

Agent需要继续修。

---

直到：

```text
verification = PASSED
```

这时候 Artifact 可能进入：

```text
status = READY_FOR_REVIEW
```

如果这个任务还需要人决定：

用户再审核。

用户接受以后：

```text
status = ACCEPTED
```

所以一个成果其实可能经历：

```text
DRAFT
↓
VERIFIED
↓
REVIEWED
↓
ACCEPTED
↓
PUBLISHED
```

注意：

> **Verified 和 Accepted 不是一回事。**

Verifier只能证明：

> 它符合我们预先定义的标准。

但有些任务最终到底要不要采用，还是应该由人决定。

---

比如 Agent 给出了一个满足：

```text
5 家媒体
预算 ≤ 3000
媒体真实
价格正确
```

的方案。

Verifier全部通过。

但用户可能还是说：

> “我不喜欢这几家，换一批。”

没问题。

因为：

> **符合规则，不等于用户必须接受。**

这也再次体现了：

```text
模型负责工作
系统负责验证
人负责最终接受或高后果决定
```

---

## 十、那 Eval 又是什么？

这里特别容易把：

**Verifier**

和：

**Eval**

混在一起。

它们都在“检查”。

但检查的是完全不同的问题。

最简单可以这样理解：

> **Verifier 看一单。**
> 
> **Eval 看系统。**

---

比如这一次用户要求：

> 推荐 5 家媒体。

Verifier回答的是：

```text
这一次推荐结果
有没有达到 Done Criteria？
```

也就是：

> **这次任务到底有没有完成？**

---

但产品上线以后，我们可能跑了 1000 个任务。

我们真正关心的是：

```text
总体成功率是多少？
推荐质量稳定吗？
选错 Tool 的比例是多少？
平均需要多少步？
多少任务陷入循环？
越权发生过几次？
用户有多少次重新修改？
哪个模型版本更好？
换了新 Skill 以后有没有退化？
```

这就是：

**Eval**

它在回答：

> **这个 Agent 系统整体到底靠不靠谱？**

---

所以可以用一句很容易记住的话：

```text
Verifier
= 这一单过没过？
Eval
= 这个系统长期行不行？
```

---

## 十一、为什么传统软件的 Test 还不够？

那可能有人会问：

> 有 Test 不就行了吗？为什么还要 Eval？

因为传统软件和 Agent 有一个非常大的区别：

> **传统代码的路径通常比较确定，Agent 的行为具有概率性。**

比如传统函数：

```text
add(1, 2)
```

我们预期：

```text
3
```

每次都一样。

---

但 Agent 面对：

> “帮我为这篇文章选 5 家媒体。”

同样输入运行两次，它可能：

```text
第一次：
A B C D E
第二次：
A B C F G
```

路径甚至也不一样。

一次可能调用：

```text
search → filter → price
```

另一次可能：

```text
search → history → filter → price → search again
```

因此我们不能只测试：

> 某个函数有没有返回正确结果。

还需要看：

```text
它选 Tool 对不对？
路径合理不合理？
有没有重复调用？
有没有违反安全边界？
最终结果质量够不够？
成本是不是失控？
失败以后会不会正确处理？
```

所以传统测试仍然需要。

但还要在上面再增加：

> **针对 Agent 行为和结果的 Eval。**

---

## 十二、Eval 不只是检查最终答案

一个 Agent 最后给出的结果可能看起来很好。

但它中间是怎么得到的，也很重要。

例如两个 Agent 最后都找到了正确答案。

Agent A：

```text
搜索
↓
读取权威来源
↓
分析
↓
验证
↓
完成
```

一共 4 步。

Agent B：

```text
搜索
↓
搜索
↓
搜索
↓
调错 Tool
↓
重试
↓
又调错 Tool
↓
猜了一个结果
↓
碰巧答对
```

一共 27 步。

如果只看最终答案：

> 两个都是对的。

但你肯定不会认为：

> 两个系统一样可靠。

所以 Eval 至少需要看几层。

---

### 1. Tool

> Tool 有没有选对？

比如本来应该：

```text
get_media_price()
```

却调用了：

```text
search_web()
```

那就是 Tool 选择有问题。

---

### 2. Skill

> 正确的专业方法有没有触发？

比如做媒体推荐时：

> 有没有用媒体推荐 Skill？

而不是直接凭模型常识生成。

---

### 3. Trajectory

也就是：

> **整个路径走得怎么样？**

例如：

```text
有没有重复调用
有没有无意义循环
有没有漏掉关键步骤
审批前有没有执行高风险动作
遇到错误以后有没有正确调整
```

---

### 4. Outcome

最终：

> **目标到底有没有完成？**

比如：

```text
推荐质量
事实正确率
任务成功率
专家评分
```

---

### 5. Safety

> **有没有越界？**

例如：

```text
没有批准就下单
读取了不该读取的数据
外部内容改变了系统规则
泄露敏感信息
```

这类错误可能一次都不能接受。

---

### 6. Online

最后进入真实用户以后，还要看：

```text
用户修正率
放弃率
任务成功率
事故率
成本
延迟
```

因为实验室里 Eval 很高：

> 不代表真实用户就觉得好用。

对 Agent 的评测因此不能只看最终文本，还需要看 Tool、Skill、Trajectory、Outcome、Safety 以及真实在线表现。

---

## 十三、Eval Dataset 从哪里来？

既然要 Eval，就需要：

> 测试题。

也就是 Eval Dataset。

刚开始可以从真实业务里挑一些典型任务。

比如媒体推荐 Agent。

准备：

```text
任务 001
标准企业科技稿
预算充足
任务 002
预算特别低
任务 003
文章跨多个行业
任务 004
用户最近已经发过大量媒体
任务 005
媒体数据库缺报价
任务 006
用户要求使用不存在的媒体
任务 007
目标非常模糊
任务 008
出现冲突信息
```

不是只准备：

> 最容易成功的情况。

还应该专门准备：

```text
缺数据
冲突
边界条件
模糊目标
错误输入
越权诱导
```

因为真正上线以后，用户不会按照我们 Demo 时最理想的方式使用系统。

---

还有一个特别重要的来源：

> **生产失败。**

比如上线以后发现：

> Agent 在“报价更新过程中”偶尔会混用新旧价格。

那这次事故不能修完就算了。

应该把这个案例加入：

```text
Eval Dataset
```

以后每次：

```text
换模型
改 Prompt
改 Skill
改 Tool
改 Context
```

都重新跑一次。

这样同一种错误才不会下次再回来。

生产中的失败样本本来就应该持续回流到 Eval，并成为后续模型、Prompt、Skill 和 Tool 更新时的回归样本。

---

## 十四、为什么不能只看“平均分”

还有一个很危险的问题。

假设我们的 Agent 测试了 1000 次。

成功 980 次。

于是：

```text
成功率 = 98%
```

看起来非常好。

但剩下的 20 次是什么？

如果只是：

> 推荐理由写得不够好。

可能还能接受。

但如果其中一次是：

> 没有用户批准就扣了钱。

那：

> 98% 的平均成功率没有任何意义。

---

所以对于一些高风险问题，需要的是：

**Hard Fail**

也就是：

> **发生一次都不能通过。**

例如：

```text
越权写入
→ 0 次
重复扣费
→ 0 次
伪造来源
→ 0 次
未批准正式发布
→ 0 次
敏感信息泄露
→ 0 次
```

即使其他指标全部 99.9%：

> 这些红线出了问题，还是不能上线。

因为平均数很容易把严重问题藏起来。

所以 AI Native 系统不能只问：

> “平均表现有多好？”

还应该问：

> **“有没有绝对不能发生的事情发生了？”**

对于越权写入、伪造引用、重复创建和敏感信息泄露这类严重问题，应该设置硬阻断，而不是让漂亮的平均任务成功率把它们盖过去。

---

## 十五、我们重新看一次完整的“完成”过程

还是我们的发稿产品。

用户目标：

> “给我做一份 3000 元以内、包含 5 家媒体的发布方案。”

系统一开始就有：

**Goal**

```text
生成媒体发布方案
```

**Done Criteria**

```text
媒体数 ≥ 5
总价 ≤ 3000
至少 1 家权威媒体
无近期重复媒体
价格来自当前数据库
每家都有推荐理由
```

---

Agent 开始工作。

生成：

```text
PLAN-001
```

内容：

```text
媒体 A ¥800
媒体 B ¥700
媒体 C ¥600
媒体 D ¥500
媒体 E ¥450
总价：
¥3050
```

Agent可能觉得：

> “方案质量不错。”

但 Verifier 一跑：

```text
媒体数量 ✅
权威媒体 ✅
无重复 ✅
价格真实 ✅
预算：
3050 > 3000
❌ FAILED
```

所以：

> 不能完成。

---

Agent收到验证结果：

```text
预算超出 ¥50
```

重新调整。

得到：

```text
总价：
¥2950
```

Verifier再次执行：

```text
数量 ✅
预算 ✅
权威媒体 ✅
无重复 ✅
价格 ✅
理由 ✅
```

结果：

```text
VERIFIED
```

于是：

```text
PLAN-001
status = READY_FOR_REVIEW
```

---

然后交给用户。

用户：

> “可以，就这版。”

系统记录：

```text
status = ACCEPTED
```

注意这里经历了：

```text
Agent 生成
↓
Verifier 验证
↓
用户接受
```

而不是：

```text
Agent：
我觉得好了。
↓
Done
```

这就是一个非常大的区别。

---

## 十六、所以“完成”其实有不同层次

我们平时很容易把：

> Done

理解成一个状态。

但实际系统里，可以把它拆得更细一点。

比如：

```text
Generated
Agent 已经生成结果
↓
Verified
系统确认符合标准
↓
Reviewed
人已经看过
↓
Accepted
用户正式接受
↓
Executed
真实动作已经执行
↓
Confirmed
外部世界已经确认成功
```

不同任务需要到哪一层才算 Done，是不一样的。

比如：

> 生成文章草稿。

可能：

```text
Verified
```

就足够了。

但是：

> 帮用户正式发布。

仅仅：

```text
Artifact 已生成
```

肯定不够。

必须至少到：

```text
订单已提交
↓
供应商成功
↓
发布链接已回读
```

才可能真正完成。

所以：

> **Done 本身也是一个业务定义，而不是模型说的一句话。**

---

## 十七、一个真正可靠的系统，应该让 Agent 自己跑 Verifier

这里还有一个非常重要的变化。

Verifier不是一定要：

> 等用户来检查。

最好是 Agent 自己就能够调用。

比如 Coding Agent 修改完成后：

```text
运行测试
```

失败：

```text
❌
```

它自己看到：

> 还没做完。

继续修。

再运行：

```text
✅
```

才停止。

---

媒体推荐也是一样：

```text
生成方案
↓
run_plan_verifier()
↓
失败：预算超限
↓
继续调整
↓
run_plan_verifier()
↓
通过
↓
提交成果
```

你会发现：

> **Verifier其实是 Agent Loop 的反馈信号。**

它告诉 Agent：

```text
通过
失败
未知
```

而不是让 Agent依靠一种模糊感觉：

> “应该差不多了吧。”

这正是一个 Agent 能不能逐渐放手自主工作的关键。

每个重要目标最好都有 Agent 可以自行运行的验证方式，而不是依赖模型自己反思“应该没问题”。

---

## 十八、Model × Harness × Environment × Verifier 到这里才真正闭环

现在回头看我们前面一直讲的那个公式，就会更容易理解：

```text
Agent System
=
Model
×
Harness
×
Environment
×
Verifier
```

### Model

负责：

> **判断下一步应该干什么。**

---

### Harness

负责：

> **让 Agent 可以持续运行。**

---

### Environment

负责：

> **给它一个可读、可做的真实工作世界。**

---

### Verifier

负责：

> **告诉它到底做对没有、做完没有。**

缺了 Verifier 会发生什么？

Agent依然可以：

```text
想
↓
做
↓
继续想
↓
继续做
```

但它缺少一个可靠的：

> **停止信号。**

于是它可能：

> 太早停。

或者：

> 一直不停。

甚至：

> 做错了还非常自信地告诉你完成了。

所以真正完整的 Agent Loop 更应该是：

```text
Goal
↓
Plan
↓
Action
↓
Observe
↓
Verify
↓
没通过
→ 调整 → 继续
通过
→ Done
```

这时候整个系统才真正闭环。

---

## 十九、所以怎么知道 AI Native 系统真的完成了？

现在可以重新回答这一章的问题。

不是因为：

> **Agent 说完成了。**

也不是因为：

> **用户看起来觉得还行。**

而是应该有一条完整的完成链路：

```text
Goal
先定义想完成什么
↓
Done Criteria
提前定义怎样才算完成
↓
Agent Work
Agent 开始执行
↓
Artifact
形成真正的工作成果
↓
Evidence
保留事实和来源
↓
Verifier
独立检查是否满足完成标准
↓
Human Acceptance
需要的时候，由人做最终接受
↓
Done
```

而在整个产品层面，还需要：

```text
Eval
```

持续回答另一个更大的问题：

> **这个 Agent 系统长期到底靠不靠谱？**

所以可以记住两个特别简单的问题：

```text
Verifier：
这一单，真的完成了吗？
Eval：
这个系统，一直都能做好吗？
```

## 二十、但即使我们做了这么多，Agent 还是一定会失败

到这里，我们已经解决了：

```text
怎么思考
↓
怎么行动
↓
怎么不失忆
↓
怎么不乱来
↓
怎么证明完成
```

看起来一个 AI Native 系统已经非常完整了。

但最后还有一个我们不可能绕过去的问题：

> **Agent 一定会失败。**

可能是：

```text
模型判断错了
Context 缺数据
Tool 挂了
第三方接口超时
权限不足
数据库状态冲突
Verifier 没通过
用户一直没批准
网络在提交瞬间断了
```

真正成熟的软件不能假设：

> “这些事情不要发生就好了。”

而应该从一开始就问：

> **发生以后怎么办？**

特别是有一种情况最麻烦：

Agent创建订单时网络突然断了。

现在它根本不知道：

> **订单到底创建成功没有。**

如果直接再创建一次：

> 可能重复下单。

如果当作已经成功：

> 又可能实际上根本没创建。

所以下一章我们就来解决：

**要是 AI Native 系统失败了怎么办**

下一篇会把 **Error、Trace、Readback、Idempotency、Checkpoint、Recovery 和 Rollback** 真正串起来。

也就是：

> **不是怎么让 Agent 永远不失败，而是怎么让它失败以后知道发生了什么、保住已经完成的工作，并且从一个确定的位置继续。**
