# 要是 AI Native 系统失败了怎么办

前面几章，我们已经把一个 AI Native 系统需要解决的几个核心问题基本讲完了。

它现在可以：

```text
理解目标
↓
根据 Context 和 Skill 做判断
↓
调用 Tool 做事
↓
用 State 保存进度
↓
在 Guardrail 和权限边界里行动
↓
用 Verifier 判断到底有没有完成
```

看起来已经很完整了。

但如果真的把这样的系统放进生产环境，还有最后一个问题绕不过去：

> **它一定会失败。**

而且这里的“失败”，远不只是：

> 模型偶尔答错一道题。

因为一个真正的 Agent 已经会：

- 调接口；
- 写数据；
- 创建订单；
- 修改文件；
- 调用外部服务；
- 等待人工；
- 连续工作几十分钟甚至更久。

任何一个环节都有可能出问题。

比如：

```text
模型判断错了
Context 缺了一份关键资料
Tool 调用失败了
第三方 API 超时了
用户没有权限
数据库状态冲突了
Verifier 没有通过
任务执行到一半服务重启了
用户批准以后网络突然断了
```

所以真正成熟的 AI Native 系统，不能建立在一个假设上：

> **“只要我们把 Agent 做得够聪明，它就不会失败。”**

更现实的设计应该是：

> **失败一定会发生，所以从第一天开始，就要设计它失败以后怎么办。**

---

## 一、失败以后，第一件事不是 Retry

很多系统遇到错误以后，最简单的处理方式就是：

```text
失败
↓
Retry
```

再失败：

```text
Retry
```

还失败：

```text
Retry
```

这对一些纯读取操作可能问题不大。

比如：

> 查询天气接口超时。

重新查一次，也许就好了。

但对于一个会改变现实世界的 Agent 来说：

> **“再试一次”有时候反而是最危险的处理方式。**

比如 Agent 正在创建一张发布订单：

```text
create_order()
```

请求发出以后，网络突然断了。

Agent看到：

```text
Timeout
```

这个 Timeout 到底代表什么？

不一定代表：

> 创建失败。

也有可能是：

```text
Agent
   ↓
请求已发送
   ↓
服务器成功创建订单
   ↓
服务器准备返回结果
   ↓
网络断开
   ↓
Agent 没收到结果
```

也就是说：

> **服务器已经成功了，只是 Agent 不知道。**

如果这时候 Agent直接：

```text
Retry create_order()
```

可能发生：

```text
订单 1：OUR-1001
订单 2：OUR-1002
```

一篇文章被下了两次单。

所以处理失败之前，首先要搞清楚：

> **到底发生了什么？**

---

## 二、失败不是一种状态，而是很多不同的问题

我们平时很容易把错误统一理解成：

```text
ERROR
```

但真正的软件不能这样。

因为不同错误，需要完全不同的处理方式。

比如：

### 第一类：信息不够

```text
缺品牌信息
缺预算
缺文件
缺用户授权
```

这种情况下正确动作不是重试。

而应该：

> **补信息。**

---

### 第二类：模型判断错了

例如 Agent 选了一家不符合要求的媒体。

Verifier 返回：

```text
FAILED:
MEDIA_NOT_MATCHED
```

这时候正确动作可能是：

> 重新判断，换一个候选。

---

### 第三类：Tool 暂时坏了

例如：

```text
get_media_price()
→ 503 Service Unavailable
```

这种可能是暂时性错误。

可以：

> 等待以后重试。

---

### 第四类：权限不足

```text
create_order()
→ PERMISSION_DENIED
```

这个时候重试一百次也没有意义。

正确做法应该是：

> 找到有权限的人，或者停止。

---

### 第五类：业务状态冲突

比如 Agent 准备创建订单。

结果系统返回：

```text
ORDER_ALREADY_EXISTS
```

这不是系统坏了。

而是：

> **现实状态已经和 Agent 原来以为的不一样。**

它应该重新读取 State，再决定下一步。

---

### 第六类：未知状态

最麻烦的就是刚才说的：

> 请求已经发出，但不知道有没有成功。

这时候不能假设：

```text
成功
```

也不能假设：

```text
失败
```

它应该明确进入：

```text
UNKNOWN
```

然后先去查。

---

所以一个 Agent 系统的错误最好不是简单的：

```text
success
/
error
```

而应该尽量告诉系统：

```text
VALIDATION_ERROR
PERMISSION_ERROR
CONFLICT
TRANSIENT_ERROR
UNKNOWN_RESULT
```

因为只有先知道：

> **哪里坏了。**

才知道：

> **下一步应该怎么办。**

真正的 Agent Contract 本来就应该包含错误分类、停止条件以及对应的恢复策略。

---

## 三、Trace：出事以后，首先得知道它刚刚到底干了什么

这时候就会需要一个非常重要的东西：

**Trace**

可以简单理解成：

> **Agent 的工作记录。**

不是聊天记录。

而是：

> **系统真正发生过什么。**

例如一次任务可以记录：

```text
Run:
RUN-001
Goal:
为文章生成并执行发布方案
Model:
GPT-X
Tool Calls:
10:01
search_media()
SUCCESS
10:03
get_media_prices()
SUCCESS
10:06
save_publish_plan()
SUCCESS
10:10
create_order()
TIMEOUT
Current State:
UNKNOWN_ORDER_STATUS
```

当系统出问题以后，你第一件事就可以知道：

> 它是在第几步坏的？
> 
> 调了哪个 Tool？
> 
> 参数是什么？
> 
> 返回了什么？
> 
> State 从什么变成了什么？
> 
> 用户批准过没有？

而不是面对用户一句：

> “刚刚好像卡住了。”

然后工程师开始猜。

---

所以真正需要追踪的东西可能包括：

```text
这是谁的任务？
目标是什么？
用了哪个模型？
拿了哪些 Context？
调用了什么 Tool？
Tool 返回了什么？
State 怎么变化？
有没有经过用户批准？
花了多少时间？
花了多少钱？
最后生成了什么 Artifact？
```

这些东西不是为了：

> “以后看看日志。”

而是为了让系统能够回答：

> **到底发生过什么。**

如果连发生了什么都不知道，就谈不上恢复。

---

## 四、Readback：不确定的时候，先看现实世界

再回到刚才那个最麻烦的问题。

Agent调用：

```text
create_order()
```

然后：

```text
Timeout
```

现在到底有没有创建成功？

正确的方法通常不是：

> 再创建一次。

而是：

**Readback**

也就是：

> **回头读取真实状态。**

例如：

```text
create_order(
    task_id = RUN-001
)
↓
Timeout
↓
get_order_by_task(
    task_id = RUN-001
)
```

如果返回：

```text
order_id = OUR-1001
status = CREATED
```

那说明：

> 第一次其实已经成功了。

于是继续下一步。

---

如果返回：

```text
NOT_FOUND
```

才考虑：

> 重新创建。

所以顺序应该是：

```text
不知道成功没
↓
Readback
↓
查现实世界
↓
已经成功
→ 继续
没成功
→ 再执行
```

而不是：

```text
不知道成功没
↓
先重试再说
```

对于所有存在写入副作用的操作，这个区别都非常重要。网络失败以后，正确顺序应该优先 readback，再决定是否需要重新执行。

---

## 五、Readback 其实是在解决一个非常重要的问题：模型不能决定现实发生了什么

上一章我们说过：

> 模型说“完成”，不代表现实已经完成。

失败恢复也是一样。

模型可能根据错误信息猜：

> “应该没创建成功。”

但这只是判断。

真正的事实必须去：

> **权威系统里读取。**

所以：

```text
模型：
我不知道订单是否创建成功。
↓
Readback：
去订单系统查。
↓
订单系统：
OUR-1001 已存在。
↓
State：
ORDER_CREATED
```

你会发现这里其实又回到了我们前面的原则：

> **模型负责处理不确定性，代码和权威系统负责告诉它事实。**

---

## 六、Idempotency：就算真的重试，也不能做两遍

但还有一个问题。

假设 Readback 以后确认：

> 没成功。

那我们可以重新执行。

可如果网络环境一直不稳定呢？

可能：

```text
第一次请求
超时
第二次请求
超时
第三次请求
成功
```

我们怎么保证：

> 服务端不会悄悄创建三张订单？

这就需要：

**Idempotency**

中文一般叫：

> **幂等。**

这个词听起来特别技术。

其实意思很简单：

> **同一件事情执行很多次，最终也只产生一次效果。**

---

比如第一次创建订单的时候，带一个：

```text
idempotency_key =
RUN-001_CREATE_ORDER
```

系统第一次收到：

```text
RUN-001_CREATE_ORDER
```

创建：

```text
OUR-1001
```

第二次又收到：

```text
RUN-001_CREATE_ORDER
```

系统发现：

> 这件事以前已经处理过。

于是直接返回：

```text
OUR-1001
```

而不是：

> 再创建 OUR-1002。

---

所以用户按了十次：

> “提交。”

Agent重试了五次。

网络重连了三次。

最终仍然只有：

```text
一张订单
```

这就是幂等。

---

很多现实业务非常需要这个东西：

```text
创建订单
付款
退款
创建工单
发送正式申请
扣积分
```

因为这些动作一旦重复发生，后果就很严重。

所以一个好的 Tool 不能只是：

> “可以执行。”

还要考虑：

> **重复执行会怎么样。**

创建型工具尤其应该返回稳定对象 ID，并能通过同一幂等键安全重试。

---

## 七、Checkpoint：失败以后，不要从头来

另一个特别让人崩溃的系统是什么？

你让 Agent 跑了四十分钟。

它已经：

```text
搜了 100 份资料
↓
分析了 60 份
↓
整理出初步结论
↓
写了大半份报告
```

然后第 41 分钟：

> Tool 挂了。

系统：

> “任务失败，请重新开始。”

这当然不行。

所以前面“不失忆”那一章讲的：

**Checkpoint**

在失败恢复里会再次发挥作用。

---

一个长任务应该不断留下安全节点。

例如：

```text
资料已收集
↓
Checkpoint 1
资料已筛选
↓
Checkpoint 2
分析已完成
↓
Checkpoint 3
草稿已生成
↓
Checkpoint 4
用户已批准
↓
Checkpoint 5
```

假设在创建订单时失败。

那恢复以后应该从：

```text
用户已批准
```

往后继续。

而不是：

> 重新分析文章。

---

所以失败以后首先要问：

```text
哪些工作已经真正完成？
哪些结果已经验证过？
最近一个可靠 Checkpoint 在哪里？
```

然后：

> **从那里恢复。**

而不是：

> **整单重来。**

长任务本来就应该保留阶段、已完成动作、Artifact、错误和恢复点，否则一个网络中断就会把整个任务打回原点。

---

## 八、Recovery：失败以后，不一定马上恢复，但必须知道怎么继续

这就到了：

**Recovery**

也就是：

> **恢复。**

Recovery 不一定意味着：

> 系统自己立刻修好。

它真正要求的是：

> **失败以后，有一条明确的下一步。**

比如：

### 情况一：暂时性 API 故障

```text
失败原因：
供应商 API 503
已保留：
发布方案
用户批准
订单草稿
恢复方式：
10 分钟后重新提交
```

---

### 情况二：权限不足

```text
失败原因：
当前用户没有正式发布权限
已保留：
发布方案
所有分析结果
恢复方式：
等待负责人批准权限
```

---

### 情况三：报价发生变化

```text
失败原因：
媒体 A 报价从 ¥800 变成 ¥1100
结果：
当前方案超过预算
已保留：
原方案
其他媒体
恢复方式：
重新寻找替代媒体
```

---

### 情况四：关键数据缺失

```text
失败原因：
文章没有目标地区信息
恢复方式：
向用户补问
```

---

这几种都叫：

> Recovery。

所以一个好的失败页面不应该只有：

```text
❌ 任务失败
[重试]
```

而应该告诉用户：

```text
发生了什么
已经完成了什么
什么没有完成
现在需要谁做什么
下一步有哪些选择
```

这样失败才是一个：

> **可以继续处理的状态。**

而不是一个黑洞。

---

## 九、失败时最重要的是：已经做完的东西不要丢

比如 Agent 执行一个复杂研究任务。

做到 80% 的时候发现：

> 最后一个数据源访问失败。

比较差的系统可能：

> 整个任务 FAILED。

然后前面所有东西：

> 都不展示。

但实际上前面已经有：

```text
37 份有效资料
完整证据表
初步结论
已经完成的分析
```

这些东西本身仍然有价值。

所以安全降级更合理的方式是：

```text
任务未完全完成
已完成：
37 份资料筛选
证据表
初步分析
未完成：
数据源 C 验证
原因：
API unavailable
当前结论：
尚不能作为最终结论
下一步：
恢复数据源以后继续验证
```

这比系统为了看起来完整，偷偷：

> 补一个没有证据的最终答案

靠谱得多。

当权威来源缺失、权限不明或状态不一致时，系统更应该停下高风险动作，保留已有成果、标记缺口，并提供恢复路径。

---

## 十、Fail-closed：不确定的时候，不要默认往前走

这里有一个很重要的安全思想：

**Fail-closed**

可以理解成：

> **关键地方如果不知道，就先停。**

例如：

> 不知道用户有没有批准。

那不是：

```text
大概批准了
→ 继续发布
```

而是：

```text
approval_status = UNKNOWN
↓
暂停正式发布
```

---

不知道付款是否成功：

```text
payment_status = UNKNOWN
```

不能：

> 再付一次。

先 Readback。

---

不知道当前报价是不是最新的：

> 不能用模型记忆里的价格直接下单。

重新查询。

---

所以对于高后果任务：

```text
UNKNOWN
```

最好是一个正式状态。

而不是强行塞进：

```text
SUCCESS
/
FAILED
```

因为很多事故恰恰发生在：

> **系统不知道，但为了继续工作，假装自己知道。**

---

## 十一、Retry 不是不能用，而是要知道什么错误值得 Retry

现在再回来看 Retry。

Retry当然不是错的。

关键是：

> **什么情况下 Retry？**

比如：

```text
网络临时超时
服务器 503
临时限流
```

这种：

> 可以重试。

甚至可以：

```text
第一次失败
↓
等 1 秒
第二次失败
↓
等 3 秒
第三次失败
↓
停止并报告
```

---

但有些错误：

```text
权限不足
参数错误
业务规则不允许
用户未批准
预算不足
数据缺失
```

重试没有意义。

因为问题不会因为：

> 再调用一次

突然消失。

所以错误最好还能标记：

```text
retryable = true
```

或者：

```text
retryable = false
```

这样 Harness 才知道：

> 应该再试，还是应该换一种恢复方式。

---

## 十二、Rollback：有些事情做错以后，需要撤回来

还有一类失败更麻烦。

不是：

> 没做成功。

而是：

> **已经做了，但后来发现做错了。**

这时候就需要：

**Rollback**

也就是：

> **回滚。**

---

比如 Agent 修改了一个草稿：

```text
V3
↓
V4
```

发现有问题。

可以恢复：

```text
V3
```

---

Agent修改了系统配置。

发现新配置导致异常。

可以：

```text
恢复旧版本
```

---

Agent创建了一张尚未执行的草稿订单。

发现条件有问题。

可以：

```text
cancel_draft_order()
```

这些都属于：

> 可回滚动作。

---

但这里特别重要的一点是：

> **不是所有动作都能真正 Rollback。**

比如：

```text
邮件已经发给客户
文章已经公开发布
付款已经打出去
外部系统已经处理订单
```

很多时候你没办法：

> “假装刚才没发生。”

你最多只能做：

```text
补发一封邮件
申请撤稿
发起退款
创建补偿动作
```

所以更准确地说，有些场景不是：

> Rollback。

而是：

> **Compensation——补偿。**

---

这也是为什么前面“不乱来”那一章里，我们一直强调：

> 越不可逆的动作，越要在执行之前严格验证。

因为你不能指望：

> “先让 Agent 做，做错了再回滚。”

有些事情根本回不去。

---

## 十三、所以 Tool 设计的时候，就应该提前想失败

到这里你会发现，一个真正适合 Agent 使用的 Tool，不能只定义：

```text
输入是什么？
输出是什么？
```

还要定义：

```text
可能发生什么错误？
哪些错误可以重试？
调用以后怎么 Readback？
重复调用会不会出问题？
能不能 Rollback？
不能 Rollback 怎么补偿？
```

比如：

```text
create_publish_order
```

就不应该只有：

```text
input:
media_id
article_id
```

最好还要考虑：

```text
idempotency_key
readback:
get_publish_order()
errors:
VALIDATION
PERMISSION
CONFLICT
TRANSIENT
UNKNOWN
rollback:
cancel_draft_order()
```

你会发现：

> **真正的软件工程，其实大量工作都发生在“正常流程以外”。**

Demo 只需要：

> 成功一次。

生产系统则必须回答：

> **失败的时候怎么办。**

---

## 十四、我们来看一次完整的失败过程

还是我们的发布任务。

用户说：

> “这五家媒体我确认了，直接发布。”

系统已经有：

```text
RUN-001
PLAN-001
status = APPROVED
total_price = 2950
```

Agent判断：

> 可以创建订单。

---

### 第一步：创建订单

调用：

```text
create_order(
    plan_id = PLAN-001,
    idempotency_key = RUN-001_CREATE_ORDER
)
```

请求发出。

然后：

```text
TIMEOUT
```

---

比较差的系统：

```text
失败
↓
Retry create_order()
```

---

比较成熟的系统首先记录：

```text
last_action:
CREATE_ORDER
last_result:
UNKNOWN
stage:
VERIFYING_ORDER_CREATION
```

然后：

**Readback**

```text
get_order_by_idempotency_key(
    RUN-001_CREATE_ORDER
)
```

返回：

```text
OUR-1001
CREATED
```

说明：

> 其实第一次成功了。

于是 State 更新：

```text
order_id = OUR-1001
stage = WAITING_SUPPLIER
```

没有重复创建。

---

接下来供应商接口调用：

```text
submit_to_supplier()
```

返回：

```text
503
```

错误类型：

```text
TRANSIENT
retryable = true
```

系统等待以后重试。

三次以后仍然失败。

于是：

```text
stage:
SUPPLIER_SUBMISSION_FAILED
```

但它不会删除：

```text
PLAN-001
用户 Approval
OUR-1001
```

这些全部保留。

然后告诉用户：

```text
发布任务尚未完成。
已完成：
✅ 发布方案
✅ 用户确认
✅ 正式订单创建
未完成：
❌ 供应商提交
原因：
供应商接口暂时不可用
下一步：
稍后继续提交，无需重新下单。
```

这才是一个：

> **可恢复的失败。**

---

## 十五、Trace + State + Checkpoint + Recovery，其实是一套东西

前面我们是分开讲这些概念的。

但真正工作的时候，它们是连在一起的。

```text
Trace
回答：
刚才到底发生了什么？
↓
State
回答：
现在到底是什么状态？
↓
Checkpoint
回答：
哪些地方已经确定完成？
↓
Recovery
回答：
接下来应该从哪里继续？
```

比如：

```text
Trace:
create_order 调用超时
State:
订单状态未知
Readback:
OUR-1001 已存在
State:
订单已创建
Checkpoint:
ORDER_CREATED
Recovery:
继续供应商提交
```

整个链路就非常清楚。

---

## 十六、失败不能只是用户体验问题，它还应该反过来改进系统

这一点我觉得特别重要。

假设生产里出现一次失败：

> Agent 在网络超时以后重复创建订单。

团队修了这个 Bug。

然后事情结束。

这还不够。

因为真正有价值的是问：

> **为什么系统允许这种错误发生？**

可能发现：

```text
create_order
没有幂等键
```

那就加：

> Idempotency。

---

又一次失败：

> Agent 不知道订单到底有没有创建。

那就补：

> Readback Tool。

---

又一次：

> Agent因为缺少媒体最新价格做错判断。

那可能补：

> Context。

---

又一次：

> Agent做完以后没有检查结果。

那就补：

> Verifier。

---

又一次：

> Agent越权调用了高风险 Tool。

那就补：

> Guardrail / Permission。

所以一个好的失败复盘不应该最后写：

> “以后 Prompt 写得严谨一点。”

而应该问：

```text
这次失败缺了什么？
Tool？
Context？
Skill？
State？
Verifier？
Guardrail？
```

然后把这次失败：

> **沉淀成系统能力。**

一次错误如果只换来一句新的提醒，下次很可能会换一种姿势再犯；如果它变成 Tool、规则、Skill、测试或 Verifier 的改进，系统才真正变得更可靠。

---

## 十七、每一次真实失败，都应该变成一个 Eval

这里就又跟上一章连起来了。

比如刚才的重复订单事故。

修完以后，应该新增一个测试样本：

```text
Case:
create_order 请求超时
Expected:
先 Readback
If order exists:
禁止重复创建
If order doesn't exist:
携带同一 idempotency_key 重试
```

以后：

```text
换模型
改 Harness
改 Tool
重构订单系统
```

都重新跑。

如果又出现：

> 重复订单。

系统直接：

```text
FAIL
```

这样失败才不是白失败。

---

所以一个真正成熟的 AI Native 系统应该形成一个循环：

```text
生产失败
↓
记录 Trace
↓
定位根因
↓
补 Tool / Context / Skill /
State / Verifier / Guardrail
↓
加入 Eval
↓
重新验证
↓
再次上线
```

也就是说：

> **系统的可靠性不是一开始设计出来以后就不变了，而是一次次从真实失败里长出来的。**

---

## 十八、不是所有失败都应该由 Agent 自己解决

还有一个很重要的问题：

> Agent 自己恢复到什么程度？

并不是所有错误都让 Agent：

> 自己想办法解决。

有些完全可以自动恢复：

```text
临时网络超时
→ Retry
搜索结果太少
→ 调整搜索
Verifier 不通过
→ 重新生成
```

---

有些应该暂停等人：

```text
用户没有批准
→ Human Gate
权限不足
→ 找管理员
合同存在重大冲突
→ 交专业负责人
```

---

有些应该直接停止：

```text
权限来源不可信
数据库状态冲突无法确定
安全规则被触发
预算已经耗尽
发现可能发生越权行为
```

所以 Recovery 不是：

> “Agent 必须想尽一切办法把目标完成。”

而是：

> **Agent 必须知道什么时候自己继续，什么时候等，什么时候找人，什么时候停。**

这才是真正的成熟。

---

## 十九、“没有完成”本身也可以是一个正确结果

这个观念其实特别重要。

我们经常会觉得：

> 一个 AI 系统只有给出答案才算成功。

所以模型很容易被设计成：

> 尽量给用户一个完整答案。

但在真实业务中，有时候最正确的结果就是：

> **现在不能完成。**

比如：

```text
缺少权威数据
没有必要权限
用户没有批准
第三方系统无法确认状态
证据冲突无法解决
Verifier 无法通过
```

这时候最好的系统应该明确告诉用户：

```text
当前未完成。
原因：
缺少 X。
已完成：
A、B、C。
尚未完成：
D。
继续需要：
用户提供 Y。
```

而不是为了显得智能：

> 猜一个答案出来。

所以 AI Native 系统的成功不应该定义成：

> 每次都给答案。

而应该是：

> **能完成就可靠地完成；不能完成就准确地知道自己为什么不能完成，并把工作保留下来。**

---

## 二十、所以怎么让 AI Native 系统失败以后还能继续？

现在我们可以重新回答这一章的问题。

一个真正能处理失败的 Agent 系统，大概需要这一套东西：

```text
Error Classification
先知道是什么错
↓
Trace
知道刚刚发生了什么
↓
Readback
不确定时先读取现实状态
↓
Idempotency
即使重试也不会重复产生副作用
↓
Checkpoint
已经完成的阶段留下存档
↓
Recovery
明确下一步从哪里继续
↓
Rollback / Compensation
做错以后能撤回或补偿
↓
Eval
把这次失败变成以后不会重复出现的测试
```

于是：

```text
失败
```

就不再意味着：

```text
任务结束
```

而可能意味着：

```text
失败
↓
判断发生了什么
↓
保存当前成果
↓
确认现实状态
↓
选择正确恢复动作
↓
继续
```

---

## 二十一、真正可靠的 AI Native 系统，不是一个“不会失败”的系统

如果一定要用一句话总结这一章，我觉得是：

> **可靠性不是永远不失败，而是失败以后不会失控。**

它应该做到：

```text
知道自己在哪里失败
↓
知道之前做过什么
↓
不会因为重试把事情做两遍
↓
不会丢掉已经完成的成果
↓
知道能不能继续
↓
知道应该从哪里继续
↓
真的无法继续时会停下来
```

所以一个真正成熟的 Agent，并不是：

> **一个永远都能把事情做成的超级员工。**

更像是一个拥有完整工作制度的人：

> 做事有记录，关键动作能核对，失败有存档，重试不会重复扣钱，遇到权限问题知道找人，发现事情不确定时不会瞎往前冲。

这时候 AI Native 软件才真正从：

> **“一个很聪明的 Demo”**

开始变成：

> **“一个可以放进真实业务里持续工作的系统”。**

---

## 二十二、到这里，整个 AI Native 软件其实已经串起来了

回头看前面的几章，我们真正解决的是一整套问题。

### AI Native 软件靠什么思考？

```text
Model
Instruction
Context
Skill
```

解决：

> **它凭什么知道下一步干什么。**

---

### AI Native 软件到底怎么做事？

```text
Agent Loop
Tool
Workflow
Harness
Environment
```

解决：

> **怎么从“会说”变成“真的会干”。**

---

### 怎么保证 AI Native 系统不失忆？

```text
State
Memory
Artifact
Checkpoint
```

解决：

> **任务怎么跨时间、跨会话继续。**

---

### 怎么保证 AI Native 系统不乱来？

```text
Authority
Permission
Guardrail
Human Gate
Sandbox
Budget
```

解决：

> **它到底可以自主到什么程度。**

---

### 怎么知道 AI Native 系统真的完成了？

```text
Goal
Done Criteria
Evidence
Verifier
Eval
```

解决：

> **凭什么宣布 Done。**

---

### 要是 AI Native 系统失败了怎么办？

```text
Trace
Error
Readback
Idempotency
Recovery
Rollback
```

解决：

> **出了问题以后怎么活下来。**

---

所以到最后你会发现，所谓开发一个 AI Native 软件，真正困难的地方并不是：

> **接一个最强的大模型。**

而是围绕一个用户目标，重新设计一整套工作系统：

```text
用户给出目标
↓
系统准备正确的 Context 和 Skill
↓
Model 判断下一步
↓
Harness 驱动 Agent Loop
↓
Tool 在 Environment 里真正行动
↓
State 保存真实进度
↓
Guardrail 限制行动边界
↓
Verifier 检查是否完成
↓
失败时能够 Readback、恢复和继续
↓
最终形成可保存的 Artifact
```

模型只是其中的一部分。

一个真正的 AI Native 系统最终要做到的，不是：

> **“AI 很聪明。”**

而是：

> **它有目标可以追，有环境可以工作，有能力可以调用，有状态可以续上，有边界不会乱来，有证据证明完成，失败以后还能继续。**

到了这里，我们才算稍微能回答一下：

> **AI Native 软件到底应该怎么做。**
