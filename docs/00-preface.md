# 前言：为什么我想写这篇东西

先说一下，我为什么想写这篇文章。

一方面，这些东西并不是我凭空想出来的。

过去一段时间，我看了很多关于 Agent、AI Native、Context、Harness、Skill、Verifier 的文章，也自己做了一些实践。但我越来越发现，如果只是不断地看文章、看案例，这些知识很容易变得非常零散。

所以我想用费曼学习法，逼着自己把这些东西重新讲一遍。

如果最后我能用自己的话把它讲清楚，甚至能真正拿它指导自己做一个 Agent 系统，那我才算真的理解了。

另一方面，我自己有一个比较强烈的判断：

**未来大量软件都会逐渐被 Agent 吞掉。**

这里的“吞掉”，不是说软件不存在了，而是说：

今天用户需要亲自操作的很多功能、按钮和工作流，未来可能都会逐渐退到后台，由 Agent 自己完成。

所以从这个角度来看，我越来越觉得，如果今天我们还只是按照传统 SaaS 的思路去做软件，其实挺无聊的。

因为 AI 只是帮你更快地写代码、更快地画页面、更快地实现原来的流程，并没有改变一个更根本的问题：

> **这些流程，本来还有没有必要由用户自己操作？**

这就像组织变革一样。

如果只是给原来的每个岗位都塞一个 AI，让每个人的效率提高 30%，当然有价值。

但真正有意思的问题其实是：

**既然 AI 已经出现了，原来的岗位、流程、协作方式，是不是本身就应该重新设计？**

软件也是一样。

以前我们讲 SaaS——Software as a Service，软件即服务。

如果一定要给 Agent 时代总结一句话，我反而更愿意把它理解成：

> **Agent 即结果。**

用户真正想要的，从来不是按钮，也不是功能。

用户要的是结果。

这也是为什么，我最开始做 GEO 的时候，其实目标就不只是把一个产品做出来。

GEO 本身离钱比较近，也可以复用公司已有的资源；但另外一个更重要的原因是，我希望通过完整做一个产品，积累足够多关于工程化、Agent、状态、验证、工具、环境这些事情的经验。

现在 GEO 慢慢接近尾声，我也觉得，是时候真正开始思考：

> **如果让我重新设计一个 Agent 原生的软件，它到底应该长什么样？**

过去这一段时间的实践，让我暂时总结出了下面这些原则。

---

## 一、什么才是 Agent 原生软件？

我觉得理解 Agent 原生软件，首先要理解：

**传统软件和 Agent 原生软件，满足用户目标的方式是不一样的。**

传统软件主要由一个个“功能”组成。

这些功能最常见的表现形式，就是页面、按钮、菜单、表单。

比如我要完成一个“发布文章”的目标。

传统软件可能是：

打开后台 → 新建文章 → 填标题 → 填正文 → 选择媒体 → 设置发布时间 → 提交 → 查看订单 → 查看结果。

整条路径基本都是提前设计好的。

> 1. 开发者提前决定：
> 2. 这个按钮干什么；
> 3. 下一步跳到哪里；
> 4. 什么情况下出现什么页面；
> 5. 用户应该按照什么顺序完成任务。
> 6. 所以用户其实承担了大量工作。

他需要知道：

**我要去哪里找这个功能，我应该先做什么，再做什么，以及每一个按钮到底代表什么。**

换句话说：

> **传统软件把“任务规划”这件事情，很大程度交给了用户。**

用户自己负责规划路径，软件负责执行每一个具体功能。

而 Agent 原生软件正好相反。

用户不应该先思考：

“我要点哪个按钮？”

他应该先说：

> “我要达到什么结果？”

比如：

“帮我把这篇文章发布到适合它的媒体上，预算 3000 元，希望主要覆盖 AI 和科技行业，并给我一个发布方案。”

接下来应该由系统自己去判断：

> 1. 需要读取什么信息；
> 2. 缺少什么信息；
> 3. 应该推荐哪些媒体；
> 4. 预算怎么分；
> 5. 哪些媒体符合要求；
> 6. 需要调用什么工具；
> 7. 哪些步骤需要用户批准；
> 8. 发布以后如何检查结果；
> 9. 失败以后怎么办。

所以如果让我现在给 Agent 原生软件下一个最简单的定义，我会说：

> **传统软件让用户操作功能完成目标；Agent 原生软件让用户提出目标，由系统自己组织能力、调用工具、推进任务，并最终交付结果。**

这也是整篇文章最重要的起点。

---

## 二、Agent 系统应该从目标开始，而不是从页面开始

这是我现在认为非常重要的一个变化。

我们以前做软件，通常是：

需求 → PRD → 原型 → 页面 → 接口 → 开发。

所以我们很容易一上来就讨论：

“首页长什么样？”

“这里放几个按钮？”

“左边是不是应该有菜单？”

但是做 Agent 系统的时候，我觉得这个顺序应该反过来。

第一件事情应该问的是：

> **用户到底想完成什么目标？**

然后再问：

为了完成这个目标，系统需要具备什么能力？

需要什么数据？

需要什么工具？

需要知道什么规则？

需要保存什么状态？

哪些地方需要人批准？

怎样证明任务真的完成了？

把这些事情设计完以后，最后才轮到 UI。

所以我的第二个原则是：

> **Agent 系统从 Goal 开始设计，而不是从 Page 开始设计。**

UI 当然仍然重要。

但是 UI 不应该决定系统能做什么。

它只是人在整个 Agent 工作过程中，用来：

> 1. 提出目标；
> 2. 补充信息；
> 3. 查看进度；
> 4. 进行审批；
> 5. 查看结果；
> 6. 纠正 Agent。

的一种交互方式而已。

甚至很多 Agent 原生软件最后都不一定应该长得像一个聊天机器人。

---

## 三、Agent 不应该只是一个聊天机器人

这是我现在特别想强调的一件事情。

**聊天机器人不等于 Agent。**

如果一个系统只能：

你问一句；

它回答一句；

你再问一句；

它再回答一句。

那我更愿意把它叫 Bot。

真正的 Agent 应该有能力主动推进任务。

例如用户说：

> “帮我完成一次媒体发布。”

真正的 Agent 接下来应该能够：

- 读取用户当前项目状态；
- 读取文章；
- 分析文章；
- 查看可用媒体；
- 调用推荐能力；
- 形成方案；
- 发现预算超标后重新调整；
- 请求用户批准；
- 批准以后调用发布工具；
- 持续检查履约状态；
- 最后交付发布结果。

所以 Agent 的核心不是：

> **它会不会聊天。**

而是：

> **它能不能围绕一个目标持续采取行动。**

聊天框只是它和人的一个接口。

---

## 四、不是所有事情都应该交给 Agent

理解 Agent 以后，很容易出现另外一个极端：

什么都交给 Agent。

我现在反而越来越觉得，这是一个非常危险的方向。

Agent 最有价值的地方，是处理：

**存在变化、需要理解、需要判断、无法提前完全写死的事情。**

比如：

- 这篇文章适合哪些媒体？
- 用户的真正意图是什么？
- 当前失败以后应该换什么方案？
- 这份材料里哪些信息最重要？
- 这些事情如果全部靠代码写规则，会非常复杂。
- 这时候模型的动态判断能力就有价值。
- 但是另外一些事情，本身就是确定性的。

比如：

这个用户有没有权限；

账户还有多少钱；

订单有没有扣过款；

这个订单 ID 是否存在；

一笔钱只能扣一次；

这个字段是否符合格式。

这些东西就不应该让 Agent“判断”。

应该直接交给代码。

所以我现在比较认同一个简单的原则：

> **理解和判断交给 Agent；确定性和唯一性尽量交给代码。**

尤其是权限、金钱、订单、状态这些事情。

Agent 可以提出：

“我认为应该退款。”

但是最后能不能退款、退多少钱、有没有重复退款，应该由确定性的系统负责。

所以设计 Agent 原生系统，不是把软件全部变成 AI。

反而是重新划分：

> **什么应该由模型判断，什么必须由代码保证。**

---

## 五、先设计 Agent 的工作环境，再设计聊天框

如果 Agent 真正需要帮用户做事情，那么我们首先应该解决的，并不是聊天框长什么样。

而是：

> **这个 Agent 到底在什么环境里面工作？**

它能看到什么？

它能调用什么？

它有什么权限？

它能修改什么？

做完以后怎么知道自己真的成功了？

失败以后能不能恢复？

做了一半以后换一个模型还能不能接着做？

这些东西比 UI 更重要。

这和传统软件其实是一样的。

如果底层能力不成立，页面做得再漂亮也没有意义。

所以我的另一个原则是：

> **先把 Agent 干活的环境设计好，再设计人怎么和它交互。**

这里面至少涉及接下来的几个问题。

---

## 六、Agent 使用的 Tool 必须是真正“可以做事”的

Agent 最终想要改变现实世界，就一定需要工具。

比如：

查询数据库；

创建订单；

发布文章；

读取网页；

发送邮件；

搜索媒体；

查询发布状态。

这些东西不能只存在于模型的描述里。

模型不能说：

“我已经帮你发布完成了。”

然后我们就相信它。

Agent 应该调用一个真实的 Tool：

`publish_article()`

工具执行完成以后，再把真实结果返回给 Agent。

所以我现在理解的 Tool，本质上就是：

> **Agent 可以调用的行动接口。**

而且这些 Tool 最好不要给 Agent 一个特别模糊、特别巨大的权限。

比如不要直接给它：

> “随便操作数据库。”

更好的方式是给它：

> “创建发布订单。”
> 
> “查询订单状态。”
> 
> “取消未执行订单。”

每一个工具负责相对明确的事情。

这样即使 Agent 判断错了，它能够造成的影响也是有边界的。

同时，Agent 操作以后应该能够 readback。

也就是：

> **做完以后，还能重新读取现实状态，确认刚才到底发生了什么。**

不是只相信 Tool 返回一句“success”。

---

## 七、Agent 说“完成了”不算完成

这是我觉得 Agent 系统里面最重要的原则之一。

模型非常容易说：

> “任务已经完成。”

但它说完成，并不能证明事情真的完成。

比如 Agent 说：

“文章已经发布成功。”

我们应该问：

发布链接在哪里？

页面真的可以访问吗？

订单状态是什么？

供应商返回了什么？

数据库记录有没有变化？

所以任何重要任务都应该存在“完成证据”。

不同任务的证据可以不同。

可能是：

readback；

自动测试；

数据库状态；

规则检查；

日志；

Verifier；

或者最后的人类验收。

所以：

> **Agent 的输出不是事实，现实世界的状态才是事实。**

Agent 可以认为任务完成。

但真正决定任务是否完成的，应该是独立证据。

---

## 八、失败以后，不应该只知道“再试一次”

Agent 肯定会失败。

这一点没什么可怕的。

真正的问题是：

> **失败以后，我们知不知道为什么失败？**

比如一次任务失败，至少应该区分：

- 是缺少信息？
- 工具坏了？
- 权限不足？
- 外部平台异常？
- 还是一开始的规则就设计错了？
- 知道原因以后，再决定下一步。
- 缺信息，就补信息。
- 权限不足，就请求权限。
- 工具异常，就重试或者切换工具。
- 规则有问题，就重新规划。

而不是无脑：

Retry。

Retry。

Retry。

因为如果 Agent 连自己为什么失败都不知道，只会不断重复同一个动作，那么所谓的“自动重试”，最后很可能只是：

> **自动制造更加昂贵的混乱。**

而且允许 Agent 重试的另外一个前提，是系统应该具备比较好的恢复和回滚能力。

否则 Agent 每试一次，都可能在现实世界留下新的脏状态。

---

## 九、长任务不能依赖聊天记录和模型记忆

这是我实践过程中感受特别明显的一件事情。

Agent 真正做复杂任务以后，很容易遇到：

上下文越来越长；

Token 不够；

网络中断；

进程退出；

模型切换；

上下文压缩；

几天以后继续任务。

如果所有进度都只存在聊天框里面，那整个系统其实非常脆弱。

因为：

> **聊天记录不是任务状态。**

模型 Memory 也不能承担核心业务状态。

因为你无法保证：

模型什么时候会调用这段记忆；

它记住了什么；

有没有被压缩；

换一个模型以后还能不能继续使用。

所以真正重要的状态，必须存在模型外部。

比如数据库。

例如一次发布任务做到一半：

用户已经批准；

订单已经创建；

供应商已经提交；

但现在不知道供应商有没有真正发布成功。

这个状态应该被明确保存。

这样即使现在把 GPT 换成 Claude，或者模型上下文全部清空，新的 Agent 只要读取状态，就知道：

> “现在不是重新发布，而是应该继续查询供应商结果。”

所以我的原则是：

> **模型负责思考，系统负责记住。**

长任务必须能够 Resume。

---

## 十、所有进度都应该变成“可恢复的状态”

这一点其实是上一条的进一步延伸。

Agent 工作的时候，不应该只留下：

聊天记录。

还应该留下结构化的任务状态。

比如：

当前目标是什么；

当前做到哪个 Stage；

哪些事情已经完成；

哪些事情正在等待；

哪些事情失败；

失败原因是什么；

下一步是什么；

是否正在等待用户审批。

这样整个 Agent 系统才真正具备“续作能力”。

你甚至可以把 Agent 换掉。

只要 State 还存在，新的 Agent 就可以继续工作。

---

## 十一、Agent 必须有明确边界

Agent 有判断能力，不代表它应该拥有无限权限。

恰恰相反。

Agent 越聪明，系统越需要清楚告诉它：

哪些事情可以做；

哪些事情不可以做；

哪些事情必须请求批准；

哪些字段不能修改；

哪些资源只能读取；

哪些动作必须经过代码验证。

尤其面对：

钱；

权限；

用户数据；

生产数据库；

外部发布；

删除操作。

这些事情不能靠提示词里面写一句：

> “请谨慎操作。”

真正重要的限制应该尽可能变成硬限制。

也就是：

> **不是告诉 Agent“不要这么做”，而是让系统本身就不允许它这么做。**

---

## 十二、Context 不应该一次性全部塞给 Agent

另外一个很容易出现的问题就是：

既然 Agent 需要 Context，那是不是把所有东西都塞进去？

我现在觉得答案恰恰相反。

Context 应该遵循一个原则：

> **此时此刻需要什么，就给什么。**

Agent 当前在做媒体推荐，就给：

文章；

品牌信息；

媒体规则；

预算；

当前任务状态。

至于数据库备份规则、部署文档、售后规则，如果当前任务根本用不到，就没有必要全部塞进去。

但这不代表其他信息不存在。

应该给 Agent 一个地图或者目录。

让它知道：

> “如果需要某类信息，可以去哪里找。”

这就是我理解的渐进式披露。

先给最相关的信息。

需要的时候，再继续展开。

而不是一次性把整个世界塞进上下文窗口。

---

## 十三、Skill 不应该只是 Prompt，而应该成为系统能力

现在很多人讲 Skill，很容易把它理解成：

一段 Prompt。

但我觉得真正长期有价值的 Skill，应该越来越接近一种：

> **可管理、可测试、可升级的系统能力。**

比如：

“媒体推荐”。

最开始它可能只是一个 Prompt。

但未来它应该有：

明确输入；

明确输出；

规则；

示例；

测试集；

版本；

质量评估。

当你修改这个 Skill 以后，可以知道：

新版本到底变好了，还是变差了。

这样 Skill 才真正具有复利。

否则今天改一句 Prompt，明天改一句 Prompt，最后谁也不知道整个系统到底为什么能工作。

---

## 十四、不要为了“Agent”而 Agent

Agent 很容易让人产生一种技术上的兴奋感。

Multi-Agent。

Agent Swarm。

Agent Debate。

几十个 Agent 协作。

这些东西当然很有意思。

但是对产品来说，我觉得应该时刻记住一件事情：

> **用户根本不关心你用了几个 Agent。**

用户只关心：

结果好不好；

速度快不快；

价格贵不贵；

过程稳不稳。

如果一个 Workflow 就能完成，就不要强行 Agent。

一个 Agent 能完成，就不要为了时髦拆成十个 Agent。

复杂不是价值。

只有：

> **复杂带来的额外收益，大于复杂本身增加的成本时，复杂才有意义。**

---

## 十五、好的 Agent 原生软件，应该把“功能”藏到后台

这其实又回到了文章最开始的问题。

传统软件把能力暴露给用户：

这里有 30 个按钮，你自己组合。

Agent 原生软件应该逐渐把这些功能收到后台。

用户不用知道：

到底调用了几个 API；

经过几个 Workflow；

查了几张表；

跑了几个 Skill；

换了几个工具。

这些应该是系统内部的事情。

用户看到的应该更多是：

**目标。**

**进度。**

**需要我决定的事情。**

**最终成果。**

所以好的 Agent 原生软件，并不是功能少了。

恰恰可能是后台能力更多了。

只是：

> **用户不再需要学习这些能力。**

---

## 十六、最终形态：人给目标，Agent 工作，人验收结果

如果把前面所有东西压缩成一句话，我觉得我现在想做的 Agent 原生软件，大概就是：

> **人给目标，Agent 工作，人验收结果。**

人在最开始告诉系统：

我要什么。

Agent 自己读取 Context、查看 State、调用 Skill 和 Tool、完成动态判断、推进 Workflow。

需要重大决策的时候，让人介入。

完成以后，通过 Readback、Verifier、测试或者现实状态证明任务确实完成。

最后人验收 Artifact。

如果结果不好，人告诉 Agent：

哪里不好。

然后 Agent 在已有状态上继续修改。

而不是让用户重新从第一步开始。

所以 Agent 原生软件真正改变的，并不是：

> **把传统软件加上一个聊天框。**

也不是：

> **用 AI 把以前的代码重新写一遍。**

它真正改变的是：

> **人和软件之间的责任划分。**

过去：

- 人理解目标。
- 人规划步骤。
- 人寻找功能。
- 人操作软件。
- 软件执行命令。

未来更可能变成：

- 人定义目标。
- 系统理解目标。
- Agent 规划任务。
- 工具执行动作。
- 代码保证确定性。
- 状态系统保存进度。
- Verifier 验证结果。
- 最后由人做真正重要的判断。

这可能才是我目前理解的：

**Agent 原生软件。**
