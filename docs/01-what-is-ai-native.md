# 什么才是 AI native软件

我们现在做的很多所谓“AI 软件”，其实并没有真正变成一种新的软件。

最常见的做法是：

在原来的 SaaS 系统里加一个 AI 按钮，接一个大模型 API；或者在原来的页面旁边加一个聊天框，让 AI 帮用户总结、生成、改写。

AI 确实进来了。

但如果把 AI 拿掉以后，整个软件的菜单、页面、流程和使用方式几乎都没有变化，那么它本质上仍然是一套传统软件。

所以在讨论 Agent 原生软件以前，我们首先得搞清楚：

> **传统软件到底是什么？**

## 一、传统软件，本质上是“功能型软件”

过去几十年，我们习惯的软件大多是围绕“功能”组织起来的。

比如一个电商后台，现实世界里的业务其实很简单：

> 客户买东西，我们收钱、发货、退款、处理售后。

但是软件不能直接把这句话放进去。

产品经理和开发者会先把现实世界拆成：

```text
商品
订单
客户
库存
物流
售后
财务
```

然后再把它们做成：

```text
商品管理
订单中心
客户中心
库存管理
物流管理
售后管理
财务中心
```

用户进入系统以后看到的，就是这些菜单、页面和按钮。

所以你可以把传统软件理解成：

> **开发者先替现实世界做了一次分类，再把这些分类做成一个个功能。**

菜单代表功能域，页面代表对象，按钮代表动作，表单代表数据结构。用户必须先学会软件是怎么分类的，才能完成自己的事情。

这套设计并没有什么问题。

对于非常确定的任务，它甚至是目前最好的方式。

比如：

- 转账；
- 开票；
- 库存扣减；
- 权限配置；
- 财务关账。

这些事情有一个共同特点：

> **目标明确、规则稳定、步骤确定，而且最好不要让 AI 自由发挥。**

所以 Agent 原生软件并不是为了消灭按钮。

真正发生变化的，是另一类任务。

---

## 二、传统软件里，真正负责“完成任务”的其实是人

这是我觉得理解 Agent 原生最关键的一点。

我们以前总觉得：

> 软件帮人在做事情。

但仔细想一下会发现，传统软件里其实有很大一部分工作，一直是用户自己在做。

假设你是一个公司老板。

你今天真正想知道的是：

> **“为什么这个月利润突然下降？”**

但传统 ERP 通常不会直接帮你完成这个目标。

它会给你：

```text
销售管理
采购管理
库存管理
财务管理
费用管理
数据中心
```

然后你需要自己思考：

> 是不是销售下降了？

打开销售。

查看同比和环比。

发现销售额其实没怎么降。

于是你继续想：

> 那会不会是成本上涨？

再打开采购。

查供应商。

发现采购成本上升了。

然后继续查物流、库存、费用。

最后你自己把几个系统里的结果拼起来：

> 原来这个月利润下降，不是因为卖少了，而是供应商涨价，加上物流费用增加。

注意：

软件提供了很多数据和功能。

但是：

> **“为什么利润下降”这个任务，实际上还是你自己完成的。**

软件给你的只是零件。

负责把零件组装成答案的人，是你。

---

再比如：

> “我要给一个客户退款。”

表面上看，你只是点几个按钮。

但你的脑子里其实正在偷偷执行一套流程：

```text
1. 找到客户
2. 找到订单
3. 判断订单能不能退款
4. 找到退款入口
5. 输入退款金额
6. 提交退款
7. 查看支付渠道结果
8. 更新售后状态
9. 通知客户
```

真正负责：

- 理解目标；
- 拆任务；
- 决定顺序；
- 找功能；
- 判断结果；
- 决定下一步；

的，其实一直都是用户。

所以换一个角度看，传统软件其实是：

```text
人
├─ 理解目标
├─ 拆任务
├─ 决定顺序
├─ 找功能
├─ 判断结果
└─ 决定下一步
软件
├─ 查询订单
├─ 修改数据
├─ 执行退款
└─ 发送通知
```

也就是说：

> **过去真正承担“Agent”角色的，是人。**

人的大脑负责规划和调度，软件只负责提供一个个确定性的工具。

于是，传统软件里的用户需要寻找功能、编排步骤、记住当前做到哪里；而在 Agent 原生软件里，用户更多负责表达目标、提供必要约束、在关键节点纠偏和批准，最后验收结果。

---

## 三、为什么 AI 时代不能继续只造这种软件

传统软件最大的问题，并不是它“老”。

而是：

> **在复杂任务里，它把太多本来应该由软件承担的复杂性，交给了用户。**

以前这么设计是有原因的。

因为传统代码不擅长理解一句非常模糊的话。

如果你告诉传统程序：

> “帮我看看这个月公司经营到底出了什么问题。”

它根本不知道应该调用：

```text
销售
采购
库存
客户
费用
```

中的哪些功能。

所以我们只能把功能一个个暴露出来，让用户自己选择。

但大模型出现以后，这个前提变了。

大模型第一次可以直接处理这种东西：

> **自然语言里的目标。**

比如你说：

> “把今天的重要客户问题处理一下。”

这句话里没有：

- 页面名称；
- 按钮名称；
- API 名称；
- 明确步骤。

但是模型可以把它理解成很多潜在动作：

```text
目标：处理今天的重要客户问题
1. 查询今天的客户消息
2. 判断哪些客户比较重要
3. 找到还没处理的问题
4. 对问题进行分类
   - 售后
   - 报价
   - 投诉
   - 技术问题
5. 查询相关订单
6. 查询历史沟通
7. 形成回复
8. 高风险问题交给人工
9. 普通问题继续处理
```

一句人话，可能对应十几个软件动作。

大模型真正改变的，就是这里：

> **它能够把人的目标映射到多个潜在动作，并且根据执行结果重新决定下一步。**

过去由用户理解系统内部的功能树，现在软件可以先理解“我要完成什么”，再组织必要能力。

所以 AI 最大的价值，不应该只是：

> 帮我们更快地把旧软件写出来。

如果过去十个人两个月做一套页面，现在两个人两周做完，这当然是一种进步。

但这只是：

> **开发效率提升。**

软件本身并没有换代。

如果 AI 只是帮助我们更快写页面、按钮和 CRUD，那只是开发提速，而不是软件换代。

所以我们真正应该停止的，不是开发传统软件。

而是：

> **停止拿 AI 去继续复制过去的软件形态。**

---

## 四、什么才是 Agent 原生软件

如果传统软件的基本单位是：

> **功能。**

那么 Agent 原生软件的基本单位应该逐渐变成：

> **用户想完成的目标。**

以前开发软件，我们首先会问：

> “这个产品要有哪些功能？”

于是我们得到：

```text
查询
筛选
导出
创建
删除
发布
统计
```

然后让用户自己组合这些能力。

但 Agent 原生软件首先问的是：

> **“用户最后到底想办成什么事？”**

例如用户真正想完成的是：

> “帮我找出这个月销售下降的原因，然后告诉我最应该优先处理的三个问题。”

它可能需要：

- 查询销售数据；
- 计算环比；
- 分析客户流失；
- 分析不同产品；
- 比较不同地区；
- 找异常；
- 生成最终报告。

传统软件把这些能力分别暴露给用户。

而 Agent 原生软件会尝试：

> **自己组织这些能力。**

因此，AI 原生软件本质上是一套目标驱动的软件：用户以目标为主要入口，模型负责处理不确定性和动态决策，系统通过 Skill、Tool、持久状态、代码约束、评测以及 Artifact 等东西把工作真正完成。

换成人话就是：

> **你告诉软件想办成什么事，而不是告诉软件下一步应该点哪个按钮。**

---

## 五、用户使用软件的方式会发生什么变化

传统软件的用户流程大概是：

```text
我有一个目标
↓
我自己想怎么做
↓
我寻找功能
↓
打开页面
↓
点击按钮
↓
填写表单
↓
看看结果
↓
自己判断下一步
↓
再寻找另一个功能
```

所以用户必须了解：

> **软件是怎么设计的。**

但 Agent 原生软件希望把它变成：

```text
用户提出目标
↓
系统理解目标和约束
↓
Agent 判断下一步
↓
选择需要的能力
↓
读取数据和材料
↓
执行动作
↓
观察结果
↓
判断是否需要调整
↓
继续工作
↓
验证是否完成
↓
交付最终成果
```

所以用户的角色开始发生变化。

以前用户负责：

> **操作软件。**

以后用户更多负责：

> **定义任务。**

这里最重要的不是“按钮变成聊天框”。

聊天框只是一种输入方式。

真正改变的是：

> **到底是谁在组织软件里的这些能力。**

过去是用户。

现在逐渐变成系统。

---

## 六、Agent 和 Workflow 最大的区别：它会根据结果改变路径

传统 Workflow 通常更像：

```text
A → B → C → D
```

开发者已经提前知道应该怎么走。

比如：

```text
上传文件
↓
解析文件
↓
写入数据库
↓
生成报告
```

只要没有异常，就一直按照这个顺序执行。

但是很多现实任务没有这么确定。

比如：

> “帮我推荐 5 家适合这篇文章的媒体。”

Agent 第一次去媒体库搜索：

```text
只找到 3 家满足条件
```

它可能判断：

> 数量不够。

于是第二步放宽预算。

再次查询。

还是不够。

于是再判断：

> 可以适当放宽媒体等级，但不能放宽行业相关性。

最终找出 8 家，再排序得到 5 家。

它的路径并不是一开始完全写死的，而是：

```text
执行
↓
看到结果
↓
判断
↓
选择下一步
↓
再执行
```

这也是为什么 Agent 适合：

> **需要根据中间结果动态判断下一步的任务。**

而规则稳定、路径明确的事情，还是应该优先使用固定 Workflow。

能用 Workflow 就不用 Agent，只有动态判断真正带来价值时才应该使用 Agent。

## 七、最简单的理解：地图和出租车

我觉得可以用一个很简单的比喻理解这两种软件。

传统软件更像：

> **一张地图。**

地图告诉你：

```text
这里是银行
这里是医院
这里是商场
这里是地铁
```

它把能力和位置全部展示给你。

但是：

> **怎么走，需要你自己决定。**

Agent 原生软件则更像出租车。

你上车以后只需要说：

> “我要去机场。”

你不需要知道：

- 哪条路；
- 哪里左转；
- 从哪个高速口上；
- 从哪个出口下来。

你的责任主要是：

> **把目的地说清楚。**

司机负责：

> **规划和执行路径。**

当然，这并不代表你可以说：

> “随便开，去哪都行。”

Agent 原生软件也不是“模型想干嘛就干嘛”。

恰恰相反，软件越能自主完成工作，我们越需要把下面这些事情写清楚：

```text
Goal：我要什么？
Constraints：有什么限制？
Context：完成任务需要知道什么？
Acceptance Criteria：怎样才算完成？
```

所以变化不是：

```text
以前：定义每一步
```

变成：

```text
以后：什么都不定义
```

而是：

```text
以前：定义每一步
```

逐渐变成：

```text
定义目标
+ 定义边界
+ 定义完成标准
```

目标型并不意味着无界自主。

允许调用哪些工具、最多走多少步、什么动作需要审批、什么状态算完成，都应该提前定义。

---

## 八、未来不是所有软件都变成 Agent

这里还有一个很容易产生的误解：

> 既然 Agent 可以自己决定步骤，那以后是不是所有按钮、流程、页面都应该消失？

并不是。

很多事情就应该继续由确定性的程序完成。

比如：

```text
金额计算
权限判断
库存扣减
数据库事务
转账
正式发布
```

这些事情最重要的是：

> **准确。**

而不是：

> **聪明。**

所以一个更合理的未来软件，实际上很可能是两层：

```text
              用户目标
                 ↓
              Agent
       理解 / 判断 / 规划 / 协调
                 ↓
       ┌─────────┼─────────┐
       ↓         ↓         ↓
      Tool      Tool      Tool
    查询媒体   创建订单   查询价格
       ↓         ↓         ↓
         确定性的程序系统
```

上面的 Agent 负责：

```text
现在应该做什么？
应该调用什么能力？
得到这个结果以后下一步怎么办？
```

下面的传统程序负责：

```text
把这个具体动作准确执行出来。
```

比如 Agent 判断：

> 应该查询媒体 138 的报价。

但真正的价格不能由 Agent 猜：

```text
get_media_price(media_id=138)
↓
数据库
↓
¥800
```

也就是说：

> **模型负责处理模糊性，代码负责守住事实。**

确定且可验证的事情交给代码或固定 Workflow；模糊但低后果的事情适合模型；模糊且高后果的事情则应该“模型提出 + 代码验证 + 人批准”。

所以所谓“AI 原生”并不是：

> 把传统软件全部扔掉。

恰恰相反。

传统软件里的数据库、权限、事务、规则、状态、审计，未来仍然非常重要。

只是它们越来越可能：

> **从用户面前的功能树，退到 Agent 背后，成为 Agent 可以调用的可靠能力。**

---

## 九、真正发生变化的，是“谁在控制软件”

所以如果一定要用一句话总结传统软件和 Agent 原生软件的区别，我觉得不是：

> “以前用按钮，现在用聊天框。”

而是：

> **以前由用户自己组织软件能力；以后由软件根据用户目标组织能力。**

传统软件是：

```text
软件：
我有这些能力，你自己来用。
```

Agent 原生软件则是：

```text
软件：
你告诉我想办成什么事，
我在允许的范围里组织这些能力，
最后把结果交给你。
```

所以软件真正发生的是：

```text
功能驱动
↓
目标驱动
```

以及：

```text
用户负责操作步骤
↓
用户负责定义目标、约束和验收
```

所以，AI 原生软件并不是“传统软件 + 大模型 API”。

它真正改变的是软件的控制方式：用户不再负责一步步操作软件，而是提供目标和约束；系统则在明确边界内自己判断路径、调用能力、推进任务，最后交付可以检查、修改和继续使用的成果。

---

## 十、但知道这些，还不够

到这里，我们其实只回答了：

> **什么是 Agent 原生软件。**

但这并不能告诉我们：

> **怎么把它真正做出来。**

因为“让 AI 自己规划、自己调用工具、自己执行”听起来很简单，真正做起来却马上会碰到一堆问题：

```text
它怎么知道现在做到哪一步？
它从哪里获得真实信息？
它可以操作什么？
什么事情不能操作？
任务中断以后怎么办？
它说自己做完了，到底是不是真的做完了？
```

这也是为什么，我们不能只盯着模型本身。

同一个 GPT 或 Claude，在普通聊天框里可能只能给你建议；但是当它拥有真实文件、工具、状态、反馈、沙箱和恢复机制以后，才能逐渐从一个“会说话的顾问”，变成一个真正能够持续工作的 Agent。

Codex 和 Claude Code 给了我们一个非常好的参照。

同一个模型，放在普通聊天框里，往往只能给出建议；但当它拥有真实文件、工具、状态、测试、沙箱和恢复机制之后，它就可以持续地读取环境、执行动作、检查结果，并在失败以后继续工作。

这说明一个很重要的问题：

> **Agent 的能力，并不只由模型决定。**

真正的 Agent 系统还需要 Harness 去维持运行，需要 Environment 提供一个可以工作的世界，并且需要 Verifier 去证明事情真的完成了。

所以最终可以得到一个更完整的工程公式：

> **Agent System = Model × Harness × Environment × Verifier**

任何一项接近零，整体可靠性都会被乘成接近零。

所以接下来，我们才真正进入这篇文章最重要的部分：

> **一个 Agent 系统到底由什么组成，以及我们应该怎么开发它。**
