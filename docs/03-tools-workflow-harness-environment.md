# AI Native 软件到底怎么做事

上一章我们解决了一个问题：

> **AI Native 软件到底靠什么思考？**

它不是单纯靠一个更聪明的模型，而是 Model、Instruction、Context、Skill 一起决定：

> 它现在看到了什么、要做什么、这类事情应该怎么做，以及下一步应该怎么判断。

但这里还有一个很大的问题。

**知道该怎么做，不等于真的能做。**

比如你问普通 ChatGPT：

> “这篇文章应该发到哪些媒体？”

它可以分析完以后告诉你：

> 建议先筛选科技媒体，再查询报价，排除过去 30 天已经发布过的媒体，最后根据预算形成一份方案。

听起来非常合理。

但接下来呢？

你还是得自己：

```text
打开媒体后台
↓
搜索媒体
↓
复制价格
↓
查看历史订单
↓
筛选媒体
↓
创建方案
↓
创建订单
↓
提交给供应商
```

也就是说：

> **AI 虽然知道下一步该干什么，但真正干活的人还是你。**

这还不是真正意义上的 Agent。

一个 AI Native 软件必须跨过一道非常重要的坎：

> **从“会告诉你怎么做”，变成“真的可以在系统里把事情做掉”。**

---

## 一、Agent 真正开始“做事”，靠的是 Tool

我们先来看一个最简单的例子。

假设 Agent 判断：

> “我现在应该查询媒体 138 的最新报价。”

如果它只是一个聊天机器人，它只能告诉用户：

> “请打开媒体后台查看一下价格。”

但如果这是一个真正的 Agent，它应该可以直接调用：

```text
get_media_price(media_id=138)
```

系统返回：

```text
媒体：A
当前价格：800 元
更新时间：今天 10:32
```

Agent 拿到这个结果以后，再继续判断下一步。

这个：

```text
get_media_price()
```

就是一个 Tool。

Tool 最简单的理解就是：

> **Agent 可以调用的真实行动能力。**

如果 Model 是大脑，那么 Tool 就很像它的手。

模型负责判断：

> “我现在需要做什么？”

Tool 负责：

> **真的把这个动作执行出来。**

---

比如在一个发稿系统里，我们可能会给 Agent 这些能力：

```text
search_media()
查询有哪些媒体
get_media_price()
查询某家媒体当前价格
get_publish_history()
查询这个客户以前发过哪些媒体
save_publish_plan()
保存发布方案
create_order()
创建订单
get_order_status()
查询订单实际状态
```

这时候 Agent 才不只是：

> “我觉得你应该这么做。”

而是真的可以：

> **去做。**

这也是 Tool 最重要的意义：它把模型的“判断”，连接到了真实世界里的“动作”。

---

## 二、Tool 不是随便给 Agent 一个 API

但这里马上会出现一个新的问题：

既然 Agent 可以调用东西，那是不是把公司的 API 全部给它就好了？

比如直接给它：

```text
execute_sql()
call_any_api()
run_any_command()
```

然后跟模型说：

> “你看着办吧。”

当然不是。

这其实非常危险。

因为 Agent 最好使用的 Tool，并不是：

> **什么都能干的万能入口。**

而是：

> **一个个窄而清楚的动作。**

比如：

```text
❌ execute_database(sql)
✅ get_media_price(media_id)
```

或者：

```text
❌ call_supplier_api(data)
✅ create_publish_order(
    media_id,
    article_id,
    quoted_price,
    idempotency_key
)
```

为什么？

因为对于第一个工具，Agent 还需要自己判断：

> 表叫什么？
> 
> 字段叫什么？
> 
> SQL 怎么写？
> 
> 哪些数据能改？
> 
> 改错了怎么办？

于是大量本来应该由系统负责的事情，又重新丢给了模型。

而第二种 Tool 已经把业务语义写清楚了：

> **“查询媒体报价。”**
> 
> **“创建一张发布订单。”**

Agent 只需要判断：

> 我现在是不是应该调用它？

这才是比较合理的分工。

---

所以 Tool 其实不只是“一个接口”。

一个真正给 Agent 使用的 Tool，最好还把很多事情提前定义清楚，比如：

```text
这个 Tool 是干什么的？
需要什么参数？
返回什么？
调用成功是什么状态？
失败是什么状态？
会不会产生副作用？
能不能重复调用？
调用后怎么确认真的成功了？
```

这些东西后面讲“失败怎么办”的时候，我们还会详细讲。

现在先记住一个原则：

> **Agent 负责选择动作，Tool 负责准确执行动作。**

---

## 三、但是并不是每一步都应该让 Agent 决定

看到这里很容易走到另一个极端：

> 既然 Agent 可以自己判断下一步，那以后是不是所有流程都让它决定？

也不是。

比如你要创建一张正式订单。

系统可能要求：

```text
验证用户身份
↓
检查媒体是否存在
↓
检查当前报价
↓
检查账户余额
↓
冻结额度
↓
创建订单
↓
写入账本
```

这些步骤如果规则已经非常明确，就根本没必要每一次都问模型：

> “下一步应该干嘛？”

因为答案永远差不多。

这种东西应该直接由程序写死。

这就是：

**Workflow**

Workflow 可以理解成：

> **已经确定好的工作流程。**

例如：

```text
A → B → C → D
```

系统已经知道：

> A 完成以后去 B，B 完成以后去 C。

模型不需要参与每一个步骤。

---

而 Agent 解决的是另一种问题。

例如用户说：

> “给我找 5 家适合这篇文章的媒体。”

第一次搜索以后只找到 3 家。

现在怎么办？

可能有很多选择：

```text
要不要放宽预算？
要不要降低媒体等级？
要不要调整行业标签？
还是直接告诉用户条件太严格？
```

这个时候没有一条永远正确的固定路径。

系统必须看：

> **刚刚发生了什么。**

然后再决定：

> **下一步怎么走。**

这才是 Agent 真正应该出现的地方。

---

所以 Workflow 和 Agent 其实不是竞争关系。

更准确地说：

```text
Workflow
负责已经确定的路径
Agent
负责路径不确定时的判断
```

可以提前写死的，就尽量写死。

只有：

> **“下一步需要结合当前结果判断”**

的时候，才真正值得把决定权交给模型。

---

## 四、所以真正的软件，通常是 Agent 和 Workflow 混着用

拿发稿系统举例。

用户说：

> “帮我给这篇文章制定一个 3000 元以内的发布方案，确认以后帮我发布。”

这里面其实既有 Agent，也有 Workflow。

前半段：

```text
分析文章
↓
判断传播目标
↓
选择候选媒体
↓
发现数量不够
↓
调整搜索条件
↓
比较媒体
↓
生成方案
```

这里很多步骤需要判断。

适合 Agent。

但是到了：

> 用户已经确认方案，现在创建订单。

可能就是：

```text
验证确认状态
↓
重新读取当前报价
↓
检查余额
↓
创建订单
↓
冻结额度
↓
保存订单状态
```

这部分规则非常确定。

适合 Workflow。

所以一个真正的 AI Native 软件，并不是：

```text
传统代码
VS
Agent
```

而更像：

```text
确定的地方
→ Code / Workflow
不确定的地方
→ Model / Agent
```

两者组合。

---

## 五、Agent 真正工作的核心，是一个循环

现在 Agent 有模型了。

也有 Tool 了。

它也知道哪些地方应该走固定 Workflow。

接下来我们再看它真正执行一个任务时发生了什么。

其实 Agent 的工作过程非常像一个循环：

```text
看现在是什么情况
↓
判断下一步做什么
↓
调用一个动作
↓
看到动作结果
↓
重新判断
↓
再行动
```

再重复：

```text
Think
↓
Act
↓
Observe
↓
Think
↓
Act
↓
Observe
```

直到：

> 任务完成。

或者：

> 无法继续。

这就是一个很基础的：

**Agent Loop**

---

比如用户要求：

> “给我找 5 家科技媒体，预算 3000。”

Agent 第一次判断：

```text
应该先搜索科技媒体。
```

于是调用：

```text
search_media(category="technology")
```

系统返回：

```text
找到 27 家。
```

Agent重新判断：

> 太多了，应该结合品牌和文章内容筛选。

再调用一些数据。

最后剩下：

```text
6 家比较匹配。
```

Agent继续判断：

> 需要检查价格。

调用：

```text
get_media_prices(...)
```

返回：

```text
总价 4800 元。
```

Agent看到：

> 超预算。

于是它重新规划：

> 去掉性价比最低的一家，再寻找价格更低的替代媒体。

然后继续。

---

注意这里一个特别重要的变化：

传统 Workflow 通常是：

```text
开发者提前决定路径
```

Agent Loop 则是：

```text
运行过程中
根据环境反馈
不断决定下一步
```

所以 Agent 的“自主性”真正来自这里。

不是因为它可以说很多话。

而是因为：

> **它可以看到执行结果以后，重新决定接下来怎么走。**

Codex 这类 Agent 的运行同样不是一次简单的“请求—回答”，而是模型判断、工具调用、环境反馈、再次判断构成的持续循环。

---

## 六、但谁在维持这个循环？

现在就会遇到一个很有意思的问题。

模型自己会一直这样工作吗？

不会。

模型本身更像一次：

```text
输入
↓
推理
↓
输出
```

比如你给它一段 Context。

它告诉你：

> 下一步调用 `search_media()`。

然后呢？

谁真的去执行 `search_media()`？

工具返回以后：

> 谁把结果重新交给模型？

模型又决定调用第二个 Tool：

> 谁继续执行？

任务做了 20 分钟：

> 谁记得它现在做到哪？

工具报错：

> 谁决定要不要重新运行？

达到最大预算：

> 谁让它停止？

这里就需要一个非常关键的东西：

**Harness**

---

## 七、Harness 可以理解成 Agent 的“运行系统”

如果 Model 是大脑，Tool 是手。

那 Harness 更像：

> **让这个大脑和这些手能够持续配合工作的那套运行系统。**

它不一定直接负责业务判断。

但是它负责让整个 Agent 跑起来。

例如：

```text
把当前 Context 给模型
↓
模型说：
我要调用 search_media
↓
Harness 去执行 Tool
↓
拿到 Tool 返回结果
↓
重新加入 Context
↓
再次调用模型
↓
模型决定：
继续查价格
↓
再调用 Tool
↓
一直循环
```

这个 Loop 并不是模型凭空自己维持的。

是 Harness 在维持。

---

所以 Harness 经常会负责很多“幕后工作”。

比如：

```text
现在该调用模型了
模型可以看到哪些 Context
模型这次可以调用哪些 Tool
工具执行结果怎么返回
当前任务最多允许多少步
什么时候暂停等用户确认
什么时候停止
任务中断以后怎么继续
```

这些东西用户平时看不到。

但它们实际上决定了：

> **一个 Agent 是只能聊两句，还是能持续工作。**

Harness 负责的核心就是这些运行层能力：循环、工具路由、Context、线程、权限和恢复；它把模型变成一个可以持续行动的运行时，而不只是一次模型调用。

---

## 八、所以 Codex 不只是“一个会写代码的模型”

理解 Harness 以后，我们再看 Codex、Claude Code 这类产品就容易很多。

为什么普通聊天框里的模型，你问：

> “帮我修这个 Bug。”

它通常会：

> 给你代码。

然后你自己：

```text
复制
↓
粘贴
↓
运行
↓
看报错
↓
再复制回来
```

但 Coding Agent 可以：

```text
自己读取代码
↓
自己搜索仓库
↓
修改文件
↓
运行测试
↓
看到测试失败
↓
继续改
↓
再次测试
```

为什么？

并不是突然换成了一个完全不同物种的模型。

真正的区别之一，是：

> **它被放进了一套可以持续运行的 Harness 里。**

模型不再孤零零地回答一次问题。

而是进入：

```text
判断
→ 行动
→ 反馈
→ 再判断
```

这个工作循环里。

这也是为什么做 AI Native 软件的时候，不能只问：

> “我们用 GPT 还是 Claude？”

还得问：

> **“这个模型被放进了一套什么样的运行系统？”**

---

## 九、但是只有 Harness 和 Tool 还不够，它还需要一个可以工作的世界

假设我们现在已经有：

```text
Model
Harness
Tool
```

Agent 是不是就能工作了？

还差一样非常重要的东西：

**Environment**

Environment 可以理解成：

> **Agent 实际工作的世界。**

---

对一个 Coding Agent 来说，它的 Environment 可能包括：

```text
代码仓库
文件系统
Git
终端
测试
日志
浏览器
运行中的程序
```

Agent 可以：

> 读取这些东西。

也可以：

> 在允许范围内改变这些东西。

然后这些东西还能：

> 给它反馈。

---

对一个发稿 Agent 来说，它的 Environment 可能是：

```text
文章库
媒体数据库
客户信息
历史订单
价格系统
供应商系统
发布结果
内部规则
```

这就是它真正工作的世界。

---

所以 Environment 并不一定是：

> 一个电脑桌面。

它可以是：

```text
数据库对象
API
文件
事件流
日志
后台系统
业务状态
```

关键不在它长什么样。

关键在于：

> **Agent 能不能看懂这个世界，并且在这个世界里工作。**

---

## 十、一个好的 Environment，首先要让 Agent“看得懂”

假设你的系统里其实已经有所有数据。

但它们分别藏在：

```text
一个只有人能看的后台页面
一个微信群
一个 Excel
某个员工脑子里
一台服务器日志里
```

人可能知道：

> 去哪里找。

Agent 不一定知道。

所以做 AI Native 软件的时候，非常重要的一件事就是：

> **把原来只方便人看的工作环境，逐渐变成 Agent 也能读的工作环境。**

比如原来用户看到：

> 订单状态：处理中。

Agent 最好不是靠：

> 看一个绿色按钮猜。

而是可以读到：

```text
order.status = PROCESSING
```

原来后台页面显示：

> 已支付。

Agent应该能读取一个权威状态：

```text
payment_status = PAID
```

原来员工知道：

> “供应商 A 周末不接单。”

如果这个规则只在运营同事脑子里：

> 对 Agent 来说就等于不存在。

所以 Environment 的一个非常重要的要求就是：

> **Legible——Agent 能读懂。**

---

## 十一、然后这个世界还得真的允许它行动

光看得懂还不够。

比如 Agent 能看到：

```text
订单 123
状态：待提交
```

但它如果没有任何 Tool 可以：

```text
submit_order(123)
```

那它还是只能告诉用户：

> “现在应该提交订单了。”

所以一个真正可以工作的 Environment 还必须是：

> **Actionable——可以行动。**

Agent需要有受控的方法去改变这个世界。

---

这时候几个东西就连起来了：

```text
Environment
告诉 Agent：
世界现在是什么样
Tool
允许 Agent：
改变这个世界
Model
负责判断：
下一步应该怎么改变
Harness
负责：
让整个循环持续运行
```

这四个东西一组合，Agent 才真正开始“工作”。

---

## 十二、我们用一个完整的发稿例子看一遍

假设用户来到我们的发稿产品，说：

> “帮我给这篇文章制定一个 3000 元以内的发布方案，专业一点，至少有一家权威媒体。”

这个任务开始以后。

上一章讲的“思考系统”先起作用：

```text
Instruction
这次要完成什么
Context
文章、品牌、预算、历史数据
Skill
媒体方案应该怎么制定
Model
判断接下来做什么
```

于是 Model 判断：

> 第一步应该先分析文章，再查符合条件的媒体。

Harness 接收到这个决定。

调用：

```text
search_media(...)
```

Tool 去真实媒体数据库查询。

Environment 返回：

```text
找到 16 家候选媒体。
```

Harness 把结果交回模型。

模型重新判断：

> 需要排除最近发过的媒体。

于是调用：

```text
get_publish_history(customer_id)
```

结果回来。

模型继续筛选。

然后它判断：

> 剩下的 8 家需要查询最新价格。

调用 Tool。

结果发现：

> 最合适的 5 家总价 3700。

超过用户预算。

于是模型重新规划：

```text
保留权威媒体
↓
替换其中两家性价比较低的媒体
↓
重新组合
```

最终得到：

```text
媒体 A  1000
媒体 B   600
媒体 C   500
媒体 D   400
媒体 E   450
总价：2950
```

然后系统把它保存成一份发布方案。

这时候先不自动下单。

因为用户要求的是：

> “给我制定方案。”

用户确认之后：

```text
[确认发布方案]
```

接下来进入一个确定性更高的 Workflow：

```text
检查方案版本
↓
重新确认报价
↓
验证账户余额
↓
创建订单
↓
保存订单状态
```

这里你就能很清楚地看到：

> **Agent 并不是从头到尾胡乱自主。**

而是：

```text
需要判断的时候
→ Agent 判断
有确定流程的时候
→ Workflow 执行
要改变外部世界的时候
→ 调 Tool
整个过程怎么持续
→ Harness 管
真实数据和对象在哪里
→ Environment 提供
```

这才比较接近一个真正的 AI Native 软件。

---

## 十三、这也是为什么“接一个 API”还不能叫 Agent

我们现在经常会看到这样的产品：

用户输入：

> “帮我生成一篇文章。”

系统：

```text
调用一次大模型 API
↓
返回文章
```

这当然是 AI 功能。

但它通常还不具备我们前面讲的那种 Agent 工作循环。

因为它基本是：

```text
Input
↓
Model
↓
Output
```

就结束了。

而一个真正具有 Agent 特征的系统，更像：

```text
Goal
↓
理解当前情况
↓
判断下一步
↓
调用 Tool
↓
读取 Environment 反馈
↓
更新当前情况
↓
再次判断
↓
继续执行
↓
直到停止
```

关键不是：

> 调用了几次模型 API。

而是：

> **系统有没有让模型进入一个持续的“判断—行动—反馈”闭环。**

---

## 十四、AI Native 也不等于“搞很多 Agent”

还有一个特别容易误解的地方：

很多人一想到 AI Native 就开始设计：

```text
规划 Agent
研究 Agent
写作 Agent
审核 Agent
执行 Agent
管理 Agent
```

看起来非常高级。

但其实：

> **Agent 越多，不代表系统越 Agent Native。**

很多时候，一个 Agent 加上：

```text
好的 Tool
好的 Context
好的 Skill
好的 Environment
好的 Harness
```

已经可以解决绝大多数任务。

如果没有真实的权限隔离、专业职责隔离或者并行需求，却硬拆成十个 Agent，反而会增加：

```text
上下文传递
状态同步
责任归属
成本
错误传播
```

这些问题。

所以做 AI Native 软件的时候，最重要的不是：

> “我要几个 Agent？”

而应该先问：

> **“我这个目标到底需要哪些能力？”**

---

## 十五、一个真正“会做事”的 AI Native 软件到底长什么样

到这里，我们就可以重新回答这一章的问题：

> **AI Native 软件到底怎么做事？**

它其实是这样工作的：

```text
用户提出 Goal
↓
模型根据
Instruction + Context + Skill
判断下一步
↓
如果是确定流程
交给 Workflow
如果需要真实动作
调用 Tool
↓
Tool 在 Environment 中执行
↓
Environment 返回真实结果
↓
Harness 把结果送回 Agent
↓
Agent 再次判断
↓
继续执行
↓
直到满足停止条件
```

所以如果要把它再压缩一点：

> **Model 负责决定，Tool 负责行动，Workflow 负责确定流程，Environment 提供真实世界，Harness 负责让这一切持续运转。**

这几个东西合起来，才让一个 AI 从：

> **“会回答问题”**

真正变成：

> **“可以完成工作”。**

---

## 十六、但这里又会出现一个新的问题

到目前为止，看起来已经很完整了。

Agent 可以：

```text
自己判断
自己调用工具
自己读取结果
自己继续执行
```

但假设一个任务要跑半个小时。

它已经：

```text
分析完文章 ✅
筛选完媒体 ✅
用户批准方案 ✅
创建订单 ✅
正在等待供应商结果……
```

结果这时候：

> 服务重启了。

或者：

> 用户关掉了页面。

或者：

> Agent 的 Context 满了，需要换一个新会话。

第二天重新打开。

系统问：

> “您好，请问有什么可以帮您？”

那前面做的所有事情就白干了。

所以当 AI Native 软件开始真正接管长任务以后，会马上遇到另一个非常现实的问题：

> **它不能只会工作，它还必须记得自己工作到哪里了。**

而且这里的“记得”，绝对不能靠：

> 聊天记录。

因为订单到底有没有创建、用户到底有没有批准、钱到底有没有扣，这些东西不能靠模型：

> “我记得好像做过。”

所以接下来就进入第三章：

**怎么保证 AI Native 系统不失忆**

这一章我们会真正拆开 **State、Memory、Artifact、Checkpoint**：

为什么聊天记录不是状态，为什么“用户喜欢简洁报告”和“这笔订单已经付款”根本不是一种记忆，以及一个 Agent 怎么才能在网络中断、换会话甚至换模型以后，依然准确地从上一次停下来的地方继续工作。
