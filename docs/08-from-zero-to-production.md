# 从 0 到上线，一个 AI Native 软件到底应该怎么开发

前面几篇，我们已经把一个 AI Native 系统内部是怎么工作的拆开讲了一遍。

它需要知道：

```text
怎么思考
→ Model / Instruction / Context / Skill
怎么行动
→ Agent / Harness / Tool / Workflow / Environment
怎么不失忆
→ State / Memory / Artifact / Checkpoint
怎么不乱来
→ Authority / Permission / Guardrail / Human Gate / Sandbox
怎么证明完成
→ Goal / Done Criteria / Evidence / Verifier / Eval
失败怎么办
→ Trace / Readback / Idempotency / Recovery / Rollback
```

但如果真的准备从零开发一个 AI Native 软件，知道这些概念还不够。

因为你马上会遇到另外一组更现实的问题：

> 我第一步到底应该干嘛？
> 
> 是先选模型，还是先画页面？
> 
> Agent 到底需要哪些 Tool？
> 
> Context 到底准备多少？
> 
> 第一版要做到什么程度？
> 
> UI 应该怎么设计？
> 
> 什么时候才需要多个 Agent？
> 
> 做到什么程度才敢上线？

所以这一篇我们不再继续拆概念。

而是把前面所有东西重新组装起来，完整走一遍：

> **一个 AI Native 软件到底应该怎么从 0 做到上线。**

---

## 一、第一步不是选模型，而是先找一个值得交给 Agent 的目标

很多团队做 AI 产品的顺序是这样的：

```text
看到一个很强的模型
↓
想想它能干嘛
↓
加个聊天框
↓
再想业务怎么套进去
```

或者：

```text
先做页面
↓
列功能
↓
接几个 AI API
↓
给原来的功能加“智能”
```

这样很容易又回到我们第一篇说的问题：

> **用 AI 更快地造旧软件。**

AI Native 软件的起点应该反过来。

第一步先问：

> **用户到底想办成什么事？**

而不是：

> 我们到底想做什么功能？

---

比如我们的发稿产品。

不要一上来就说：

```text
我要做：
文章管理
媒体管理
订单中心
供应商中心
发布中心
数据看板
AI 推荐
```

这些都是能力。

它们还不是用户真正的目标。

真正的目标可能是：

> **“我给你一篇文章，你帮我在预算范围内制定一份合适的媒体发布方案，我确认以后再帮我完成发布。”**

这时候整个产品的起点就完全变了。

我们不是从：

> 有哪些页面？

开始。

而是从：

> **为了把这件事情真正办完，系统需要具备哪些能力？**

开始。

---

但也不是所有目标都值得做成 Agent。

比如：

```text
计算 200 × 17
检查余额够不够
判断一个 ID 是否已经存在
按照固定规则开一张发票
```

这种事情路径确定、规则稳定。

直接写代码或者 Workflow 就好了。

真正适合 Agent 的目标通常有几个特点：

```text
用户价值比较明确
但实现路径不是完全固定的
过程中需要理解、判断或者调整
系统能够拿到真实数据
存在可以调用的能力
最终结果能够被验证
```

比如：

> “根据这篇文章、品牌、预算和历史投放情况，为客户制定一份媒体方案。”

就比较合适。

因为这里确实存在：

> **动态判断带来的价值。**

第一版也应该优先选择这种**范围有限、工具有限、结果可验证**的目标，而不是一开始就试图做一个无所不能的超级 Agent。

---

## 二、第一份产品文档，不应该是功能列表，而应该是 Goal Contract

找到目标以后，第二步不是开始开发。

而是：

> **先把目标定义清楚。**

因为一句：

> “帮我做媒体发布。”

其实太模糊了。

到底做到什么程度才叫完成？

所以需要把它进一步写成：

### **Goal Contract**

可以理解成：

> **这项工作到底要办成什么、有什么限制、什么才算办完。**

比如：

```text
Goal
根据用户上传的文章和品牌信息，
生成一份可执行的媒体发布方案。
```

然后继续定义。

### Inputs

完成这项任务需要什么？

```text
文章
品牌信息
传播目标
预算
历史发布数据
```

### Done Criteria

什么才算完成？

```text
至少推荐 5 家媒体
总预算 ≤ 3000 元
至少包含一家权威媒体
不得推荐最近 30 天已经发布过的媒体
所有媒体必须存在于当前媒体库
所有价格必须来自当前数据库
每家媒体必须给出推荐理由
```

### Evidence

这些结论凭什么？

```text
媒体 ID
当前价格记录
历史投放记录
推荐依据
```

### Constraints

不能突破什么？

```text
预算不得超过 3000
不得使用下架媒体
不得使用用户明确排除的媒体
```

### Human Decisions

什么事情 Agent 不能自己决定？

```text
是否接受最终方案
是否正式创建发布订单
```

### Recovery

失败以后怎么办？

```text
候选媒体不足
→ 调整候选范围
媒体价格变化导致超预算
→ 重新组合方案
关键信息不足
→ 向用户补问
```

这一步看起来只是写需求。

但它实际上决定了后面几乎所有东西。

因为只有 Goal 清楚以后，你才能回答：

```text
需要什么 Context？
需要什么 Skill？
需要什么 Tool？
需要保存什么 State？
应该生成什么 Artifact？
什么需要 Verifier？
哪里要 Human Gate？
```

所以 AI Native 产品真正的第一份文档，不应该只是“功能清单”，而应该先定义目标、输入、完成标准、证据、约束、后果、人工决定和恢复方式。

---

## 三、不要继续拆功能树，而是开始拆目标树

传统软件非常习惯：

> 功能树。

比如：

```text
发稿系统
├─ 文章管理
├─ 媒体管理
├─ 用户管理
├─ 订单管理
└─ 财务管理
```

这当然还需要。

但对于 Agent 来说，更重要的是：

> **目标树。**

比如我们的主目标：

```text
Goal：
生成一份可执行的媒体发布方案
```

继续拆：

```text
理解文章
↓
理解品牌与传播目标
↓
寻找候选媒体
↓
过滤不合适媒体
↓
排除近期重复
↓
查询最新价格
↓
控制预算
↓
生成推荐理由
↓
形成最终方案
```

然后每一个子目标再问：

> 完成它需要什么能力？

于是：

```text
理解文章
→ Model + Skill
品牌信息
→ Context
查候选媒体
→ Tool
查价格
→ Tool
历史是否发过
→ Tool / State
怎么推荐
→ Skill
保存当前方案
→ Artifact
记住做到哪里
→ State
检查预算和媒体真实性
→ Verifier
```

到这里你就会发现：

以前我们讲的那些看起来很抽象的名词：

```text
Context
Skill
Tool
State
Artifact
Verifier
```

开始变得非常具体。

它们不是为了：

> “我们的架构里应该有这些东西。”

而是：

> **完成目标需要它，所以它才存在。**

这也是为什么开发顺序应该是：

```text
Goal
↓
子目标
↓
需要的能力
↓
才是具体的软件构件
```

而不是：

```text
我先造一个 Tool 平台
我先造一个 Memory 系统
我先接 MCP
↓
再看看业务怎么用
```

目标树的作用，就是让每个子目标都能映射到真正需要的 Context、Skill、Tool、State 和 Artifact。

---

## 四、第一版不要贪大，先打通一个最小闭环

有了目标树以后，一个非常大的诱惑就是：

> 全部做。

比如一下开始设计：

```text
多 Agent
长期 Memory
几十个 Tool
RAG
MCP
任务中心
审批中心
工作流中心
Agent Platform
```

然后开发三个月。

结果：

> 系统架构非常宏伟，一个真实任务都没有完整跑通。

所以第一版更合理的方式是：

> **只做一个最小垂直闭环。**

比如发稿 Agent 第一版可以只有：

```text
1 个用户角色
1 个主 Goal：
生成媒体发布方案
1 个 Agent
3 个核心 Tool：
search_media
get_media_price
get_publish_history
1 个持久 State
1 个 Artifact：
媒体发布方案
1 个 Verifier
1 个 Human Gate：
用户最终确认方案
```

甚至第一版：

> 先不真的下单。

先把：

```text
Goal
↓
Context
↓
Skill
↓
Tool
↓
State
↓
Artifact
↓
Verifier
```

跑通。

能稳定做到：

> 用户给一篇文章 → 系统自己完成分析和推荐 → 生成方案 → 验证方案满足要求 → 用户可以看、改、确认。

这已经是一个非常完整的 AI Native 最小闭环了。

第一版真正重要的是证明：

> **这种目标型交付方式真的有价值，而且系统可以可靠地完成。**

而不是证明：

> 我们拥有一个非常先进的 Agent Platform。

---

## 五、接下来才设计 Agent 真正的工作环境

目标明确以后，再问：

> **Agent 到底在什么环境里工作？**

这里其实有一个非常好用的检查方式。

只问五个问题：

```text
看得到吗？
做得到吗？
验得到吗？
续得上吗？
管得住吗？
```

对应：

```text
可读
可做
可验
可续
有界
```

这五个问题几乎可以拿来检查整个 Agent Environment。

---

### 可读：Agent 找得到它需要的信息吗？

它能不能找到：

```text
当前 Goal
规则
当前 State
用户材料
业务对象
历史数据
错误信息
Evidence
```

比如公司有一个规则：

> “客户过去 30 天已经发布过的媒体不能再次推荐。”

但这个规则只存在运营同事脑子里。

那对 Agent 来说：

> **它就不存在。**

所以 AI Native 开发很重要的一项工作，就是把原来：

> 人知道去哪找。

变成：

> **Agent 也知道去哪找。**

---

### 可做：它真的可以改变世界吗？

Agent知道：

> 现在应该查询媒体价格。

但如果系统没有：

```text
get_media_price()
```

它只能告诉用户：

> “请去媒体后台查价格。”

那真正干活的人还是用户。

所以核心动作必须逐渐变成：

> Agent 可以调用的受控 Tool。

---

### 可验：它能不能自己知道做对没有？

生成方案以后：

> Agent 能不能运行 Verifier？

比如：

```text
数量对不对？
预算有没有超？
媒体是否存在？
价格是否是真实数据？
有没有近期重复？
```

如果验证必须永远依赖：

> 用户肉眼看。

那 Agent 还很难真正放手工作。

---

### 可续：中断以后还能不能继续？

比如运行到：

```text
方案完成
用户已经批准
订单尚未创建
```

这时候服务重启。

系统能不能通过：

```text
State
Artifact
Checkpoint
```

重新恢复？

如果不能，那它仍然只适合短任务。

---

### 有界：它犯错以后能坏到哪里？

Agent拥有：

```text
哪些 Tool？
哪些数据权限？
最多花多少钱？
最多跑多少步？
哪些动作必须人工批准？
哪些目录可以访问？
哪些网络可以访问？
```

这些东西必须有硬边界。

所以一个真正适合 Agent 工作的 Environment，并不是简单地：

> “接上数据库和 API。”

而是：

> **一个可读、可做、可验、可续，而且有边界的工作世界。**

---

## 六、Context 也应该开始按照“供应链”来设计

环境准备好以后，就会遇到 Context。

最开始做 Demo 很容易：

> 把所有东西塞进 Prompt。

比如：

```text
公司规则
品牌资料
所有媒体
所有历史聊天
所有 Skill
所有 Tool 描述
过去全部订单
```

一起给模型。

刚开始东西少，可能还能跑。

后面一定越来越乱。

所以 AI Native 系统的 Context 应该更像：

> **信息供应链。**

不同东西在不同时间进入。

---

比如：

### 一直需要的短规则

```text
当前 Goal
最核心的系统规则
关键安全边界
```

可以常驻。

---

### 当前任务状态

例如：

```text
当前阶段
用户是否批准
当前 Artifact ID
最后一个错误
```

从 State 实时读取。

---

### 大量业务资料

比如：

```text
几万个媒体
大量历史订单
公司知识库
```

不要全部塞。

需要时检索。

---

### Skill

平时只需要知道：

```text
有什么 Skill
它大概解决什么问题
```

真的命中：

> 媒体推荐。

才加载：

```text
媒体推荐 Skill
```

需要其中一个参考文件时：

> 再读参考文件。

这就是渐进披露。

不是：

> **上下文窗口越大，就越应该塞更多东西。**

而是：

> **这一步做判断真正需要什么，就给什么。**

Context 本身还需要考虑来源、信任、预算和过期问题，而长任务应优先使用按需读取、结构化 State 和摘要等方式控制上下文。

Skill 也适合采用“先暴露名称和描述，需要时再加载核心内容，最后按需读取脚本和参考资料”的方式。

---

## 七、Skill 和 Tool 到了这里，就不能继续只是“Prompt 和 API”

Demo 阶段可能这样：

> 在 Prompt 里面写一套媒体推荐方法。

生产以后不够。

Skill最好逐渐成为一份正式能力。

比如：

```text
Name
媒体推荐
When to use
用户需要根据文章制定媒体方案
When not to use
用户明确指定媒体，只需要下单
Inputs
文章
品牌
预算
历史发布记录
Procedure
1. 分析主题
2. 匹配行业
3. 排除近期重复
4. 查询报价
5. 排序
6. 检查预算
Output
媒体发布方案
References
媒体选择规则 V3
Tests
典型案例
边界案例
Owner
内容运营团队
```

这样以后：

> 推荐效果不好。

你知道应该改：

> Skill。

而不是修改一个 30000 字的超级 Prompt。

Skill 本身应该拥有输入、步骤、Tool、输出结构、参考资料、测试以及负责人等清楚的契约。

---

Tool 同样不能只是：

```text
一个能调用的 API。
```

比如：

```text
create_order()
```

生产级以后至少需要想：

```text
输入是什么？
返回什么？
谁可以调？
调用会改变什么？
重复调用会怎么样？
能不能 Preview？
怎么 Readback？
失败有哪些类型？
能不能 Rollback？
怎么审计？
```

例如：

```text
create_publish_order
Input:
plan_id
idempotency_key
Permission:
只能在方案被批准后调用
Side Effect:
创建正式订单
Readback:
get_publish_order()
Errors:
VALIDATION
PERMISSION
CONFLICT
TRANSIENT
UNKNOWN
Rollback:
cancel_draft_order()
```

这时候 Tool 才从：

> “Agent 能调用一个接口”

变成：

> **Agent 可以安全操作真实业务。**

---

## 八、到这个时候，才真正知道 UI 应该怎么设计

这一步其实和传统开发顺序差别很大。

传统产品很容易：

```text
先画页面
↓
页面定了
↓
接口围着页面长
```

AI Native 软件最好反过来。

先搞清楚：

```text
Goal
State
Artifact
Evidence
Human Gate
Recovery
```

然后才知道：

> **用户到底应该看到什么。**

AI Native 软件的 UI 我觉得可以简单理解成四类。

---

### 第一类：Intent UI

回答：

> **用户怎么告诉系统“我要什么”？**

它不一定是一个纯聊天框。

可能是：

```text
自然语言
+
上传文件
+
预算
+
选择品牌
+
高级约束
```

比如：

> “帮我给这篇文章做一个 3000 元以内的发布方案。”

同时上传文章。

这就是 Intent UI。

---

### 第二类：Progress UI

Agent工作可能需要几十秒甚至几分钟。

用户不能一直盯着：

```text
正在思考……
```

而应该看到：

```text
正在分析文章 ✅
正在搜索候选媒体 ✅
正在校验历史发布 ✅
正在检查最新报价……
等待用户确认
```

用户需要知道：

> 现在进行到哪。

而不是知道：

> 模型脑子里的完整思维过程。

---

### 第三类：Artifact UI

这反而应该成为最重要的界面之一。

最终发布方案不应该只是：

> 聊天气泡里的一段 Markdown。

而应该成为真正的成果页面：

<sheet sheet-id="nnTl3m" token="CBrss7YqPhQOlptsEy8cP60Fnmd"></sheet>

用户可以：

```text
删除一家
替换一家
修改预算
查看证据
比较版本
接受方案
```

这才是真正和：

> **成果**

交互。

---

### 第四类：Intervention UI

平时不要一直打扰用户。

真正需要的时候才出现：

```text
批准
拒绝
纠偏
补充信息
恢复任务
回滚
```

比如：

```text
即将创建 5 个正式发布订单
总金额：¥2950
[确认发布]
[返回修改]
```

这时候人工介入才真正有意义。

Goal、State 和 Artifact 等核心对象明确以后，产品界面就可以围绕 Intent、Progress、Artifact 和 Intervention 四类交互来组织。

---

## 九、所以聊天框只是一个入口，而不是整个产品

这点特别重要。

很多所谓 Agent 产品只是：

```text
一个巨大的聊天框。
```

所有工作都变成：

> 用户反复要求模型重新输出。

例如：

```text
第三家换掉。
预算改成 4000。
推荐理由详细点。
第一家还是放回来。
给我看看价格。
```

这其实很累。

更好的 AI Native UI 应该逐渐变成：

```text
聊天
负责表达意图
Progress
负责看任务状态
Artifact
负责操作成果
Evidence
负责看依据
Approval
负责批准高风险动作
Recovery
负责处理失败
```

所以：

> **聊天是交互，但不是交付。**

复杂任务如果最后仍然只能靠聊天气泡管理版本、证据、审批和结构化成果，通常还没有真正产品化。

---

## 十、先把一个 Agent 做好，再考虑多 Agent

做到这里以后，很多团队会开始：

> “是不是应该拆成多个 Agent？”

例如：

```text
文章分析 Agent
媒体推荐 Agent
价格 Agent
审核 Agent
下单 Agent
总控 Agent
```

先不要急。

真正应该问的是：

> **为什么要拆？**

值得拆成多个 Agent 的原因一般只有几类。

比如：

### 权限真的不同

```text
研究 Agent
只能读
执行 Agent
可以写
```

### 专业领域真的不同

比如：

```text
法律
财务
医学
```

需要明显不同的方法和 Context。

### 可以真正并行

例如：

> 同时调研十个独立市场。

### Context 必须隔离

否则一个 Agent 的工作空间太复杂。

---

如果没有这些需求：

> 一个 Agent + 好的 Tool + 好的 Harness

往往反而更简单。

多 Agent 会额外带来：

```text
怎么交接？
状态归谁？
上下文怎么传？
谁拥有任务？
谁负责最终结果？
两个 Agent 冲突怎么办？
成本会不会翻倍？
```

所以正确顺序应该是：

```text
先单 Agent
↓
把 Harness 做好
↓
真的遇到职责、权限或者并行需求
↓
再拆多 Agent
```

常见架构也可以逐渐从单 Agent + Tools，扩展到 Manager + Specialists、Handoff Network 或 Parallel Workers，而不是为了“Agent 感”提前增加角色数量。

---

## 十一、MCP、A2A、A2UI 这些东西，也应该等真正需要连接的时候再出现

到这时候你就会发现很多现在很火的协议到底有什么用了。

比如 Tool 越来越多。

每个 Agent 都自己重新接：

```text
数据库
Slack
CRM
搜索
文件
```

非常麻烦。

这时候：

> **MCP**

开始有价值。

它主要解决：

```text
Agent ↔ Tool / Data
```

怎么用比较统一的方式连接。

---

等系统里真的出现多个独立 Agent，要互相发现能力、交接任务：

> **A2A**

开始有意义。

```text
Agent ↔ Agent
```

---

Agent需要根据任务动态告诉客户端：

> 应该展示什么结构化界面。

可以考虑：

> **A2UI**

```text
Agent ↔ UI
```

---

而系统用了不同模型、不同 Harness、不同 Tool以后，希望：

> Trace 可以统一记录。

这时候可以使用：

> **OpenTelemetry**

做跨模型、跨框架的可观测底座。

这些协议更适合被理解成：

> **插头标准。**

它们可以减少集成成本。

但不会因为：

> 接了 MCP。

系统就自动拥有：

```text
正确 State
正确权限
正确业务规则
正确 Verifier
```

协议不能代替业务设计。

---

## 十二、先把质量做到能用，再开始优化模型和成本

第一版 Agent 还有一个特别容易掉进去的坑：

> 一开始就研究 Token 怎么省。

比如：

> GPT 太贵了，我们全部换最便宜的模型吧。

结果：

```text
成功率降低
↓
用户大量返工
↓
Agent重复调用
↓
人工成本反而更高
```

所以顺序应该是：

```text
先达到任务质量
↓
建立 Eval
↓
知道哪些能力真的需要强模型
↓
再逐步优化
```

---

最后可能形成模型分工：

```text
简单分类
→ 代码 / 小模型
结构化抽取
→ 小中模型
普通内容处理
→ 中等模型
复杂分析和规划
→ 强推理模型
结果检查
→ 规则 / 独立模型
```

这才叫：

> Model Routing。

不同任务还可以有自己的 Cost Contract。

例如：

```text
质量：
专家通过率 ≥ 90%
延迟：
P50 < 12 秒
P95 < 45 秒
预算：
平均 < $0.35
单次最高 $1.2
最多模型调用：
8 次
最多 Tool 调用：
15 次
```

一旦超过预算：

> 怎么降级。

都应该提前设计。

---

## 十三、真正的成本，也不能只算 Token

假设方案 A：

```text
每次 Agent 成本 ¥2
```

方案 B：

```text
每次 Agent 成本 ¥0.5
```

看起来 B 便宜四倍。

但 B 的任务成功率差很多。

于是用户平均每十次里：

> 有三次需要人工重新处理。

每次返工半小时。

这时候：

> Token 确实便宜了。

公司反而：

> 更贵了。

所以一个 AI Native 系统真正的成本应该包括：

```text
模型成本
Tool 成本
基础设施成本
人工返工
错误成果
误操作
失败恢复
事故成本
维护复杂度
```

很多时候最贵的不是 Token，而是错误结果、人工返工、无法恢复的任务和生产事故。

---

## 十四、能跑，不等于可以上线

这一步特别重要。

Demo 阶段：

> “我跑了十次，九次不错。”

可能就够了。

生产环境完全不够。

真正准备上线之前，应该一层一层通过 Gate。

可以简单理解成：

```text
Gate 0
这里真的有必要用 Agent 吗？
↓
Gate 1
Goal、Done Criteria、Constraints 清楚吗？
↓
Gate 2
数据、State、权限，到底谁说了算？
↓
Gate 3
Context / Skill / Tool 有正式契约吗？
↓
Gate 4
任务可以持久、停止、恢复吗？
↓
Gate 5
Eval 过了吗？
↓
Gate 6
安全边界真的存在吗？
↓
Gate 7
质量、延迟和成本能接受吗？
↓
Gate 8
监控、回滚、事故处理准备好了吗？
```

这时候才逐渐有资格说：

> **Production Ready。**

从价值、Goal、Authority、Capability、Runtime，到 Eval、安全、成本和生产运维，本来就需要逐层建立发布门槛。

---

## 十五、第一天上线，也不要直接给所有用户

Agent还有一个和传统代码很不一样的地方。

即使你的业务代码没变：

```text
模型升级
Prompt 改了
Skill 改了
Context 来源改了
搜索索引变了
Tool 描述改了
```

都有可能改变 Agent 行为。

所以真正上线的时候也应该：

> **Canary——逐步放量。**

例如：

```text
第 1 阶段
内部用户
↓
第 2 阶段
5% 真实客户
↓
观察：
成功率
人工修正率
事故
成本
延迟
↓
第 3 阶段
20%
↓
稳定以后
逐步扩大
```

而且在上线以前就要知道：

```text
模型出问题怎么退回旧模型？
Skill 更新失败怎么退回 V1？
某个 Tool 有事故怎么马上停掉？
RAG 索引错误怎么切旧版本？
Agent整体不稳定能不能退回固定 Workflow？
```

所以 Agent 系统里的 Rollback 已经不只是：

> Git 回滚。

它还可能包括：

```text
Model Rollback
Skill Rollback
Tool Disable
Context Index Rollback
Workflow Fallback
```

---

## 十六、团队自己的代码库，也需要为了 Agent 重新设计

这里还有一个经常被忽略的变化。

我们一直在讲：

> Agent 的工作环境要可读。

那么 Coding Agent 自己的工作环境是什么？

就是：

> **代码仓库。**

如果你把 Codex 或 Claude Code 放进一个项目。

但所有关键东西都存在：

```text
老板脑子里
微信群聊
昨天的会议
某个开发“大家都知道”的习惯
一个没人找到的文档
```

Agent就很难可靠工作。

所以代码仓库也要逐渐变成：

> **项目自己的 System of Record。**

比如：

```text
SPEC / GOAL
我们到底要做什么
PLAN
准备怎么推进
PROGRESS
当前做到哪里
DECISIONS
为什么采用这个架构
EVAL / TEST
什么情况才算完成
TRACE / AUDIT
Agent 实际干过什么
```

这些都应该成为正式 Artifact，而不是：

> 某次对话里的临时内容。

---

然后可以有：

```text
AGENTS.md
CLAUDE.md
```

这类入口文件。

但它们应该像：

> **地图。**

而不是：

> 一本百科全书。

例如：

```text
数据库谁是权威？
哪些目录不能改？
测试怎么跑？
架构文档在哪里？
Skill 在哪里？
发布规则在哪里？
```

把这些导航放进去。

需要详细资料，再按需读取。

仓库级 Agent 指令更适合作为导航和硬规则入口，详细知识则应该进入专门文档、Skill 和规则目录。

---

## 十七、失败以后，不只是修 Bug，而要让系统真正“长出能力”

到了生产以后，Agent一定会失败。

我们前一篇已经讲过：

```text
Trace
Readback
Idempotency
Recovery
Rollback
```

但站在整个产品开发周期来看，还有一件非常重要的事：

> **每一次失败都应该回流到系统。**

比如生产发现：

> 报价刚变化时，Agent偶尔会使用旧报价。

不要只：

> 修一下 Prompt。

而应该问：

```text
缺的是 Context 新鲜度？
还是 Tool 返回值？
还是 State？
还是 Verifier？
还是价格在下单前应该强制 Readback？
```

修完以后，把这次事故加进：

> Eval Dataset。

于是以后：

```text
换模型
改 Skill
升级 Tool
改 Harness
```

都重新跑。

真正成熟的改进循环应该是：

```text
生产失败
↓
Trace 定位
↓
找出缺失能力
↓
修改 Tool / Context / Skill /
Verifier / Guardrail
↓
加入 Eval
↓
回归验证
↓
重新上线
```

这样系统才不是：

> 每次都靠人救火。

而是在：

> **一次次把失败变成自己的能力。**

---

## 十八、什么时候才值得做“Agent Platform”？

系统做到一定规模以后，团队很容易产生一个冲动：

> “我们是不是应该抽象一个 Agent 平台？”

有时候是。

但不要太早。

比如你现在只有：

> 一个媒体推荐 Agent。

就开始开发：

```text
统一 Agent Runtime
多租户 Agent 平台
通用 Memory
通用 Workflow Builder
多 Agent Orchestrator
Agent Marketplace
```

很可能大量东西最后根本用不上。

更合理的方式是：

```text
先做好第一个 Goal
↓
再做第二个 Goal
↓
看看哪些能力真的重复出现
```

比如后来发现：

媒体 Agent、调研 Agent、客服 Agent 都在重复：

```text
Run State
审批
Artifact
Trace
Eval
权限
Recovery
```

这个时候：

> 才值得把它们抽成平台能力。

也就是：

> **先有复用，再有平台。**

而不是：

> **先造平台，再等未来需求证明它有用。**

多个真实目标已经开始复用同一套 State、Eval、权限、Tracing 和 Artifact 基础以后，平台化才更有意义。

---

## 十九、最后怎么验收：不要问“我们有没有 Agent”

项目做到最后，不应该问：

> 我们是不是用了 GPT？

也不应该问：

> 我们有没有 MCP？

甚至不是：

> 我们这个产品是不是有 Agent？

而应该回到那五个非常基础的问题。

---

### 可读

新的 Agent 进来以后，不需要人现场口头教学，也可以找到：

```text
Goal
规则
State
Evidence
当前 Artifact
```

吗？

---

### 可做

它能不能通过受控 Tool：

> **自己完成核心工作？**

还是最后总得叫人：

> “请您手动点击这个按钮。”

---

### 可验

它能不能自己获得：

```text
PASS
FAIL
UNKNOWN
```

而不是：

> “我感觉应该做好了。”

---

### 可续

刷新页面、网络中断、切换会话、甚至换模型以后：

> 还能继续吗？

---

### 有界

如果 Agent 判断错了：

```text
越权
超预算
重复写
高后果动作
```

会不会真的被系统拦下来？

这五个问题如果都可以拿出真实证据回答：

> **是。**

那这个领域才真的开始变成：

> **一个 Agent 可以可靠工作的环境。**

---

## 二十、最后再看看自己有没有掉进这些坑

还有一个特别简单的自查办法。

看看你的系统是不是这样：

### AI Button

```text
原来的软件完全没变
+
旁边多一个“AI 生成”
```

---

### Chatbot Skin

```text
什么都塞进聊天框
没有真正的 State
没有 Artifact
```

---

### Prompt Monolith

```text
所有规则
知识
方法
流程
格式
全部塞进一个超级 Prompt
```

---

### Fake Agent

```text
一次模型调用
或者固定 Workflow
包装成：
“智能自主 Agent”
```

---

### Model as Database

```text
订单是否完成？
用户是否批准？
靠模型“记得”
```

---

### Toolbox Dump

```text
几十个 Tool
一次全部扔给 Agent
```

---

### Multi-Agent Theater

```text
没有真正的职责隔离
也没有并行需求
但先设计十个 Agent
```

---

### Unbounded Loop

```text
没有最大步数
没有预算
没有停止条件
```

---

### Approval Spam

```text
Agent 每动一下
用户确认一次
```

---

### Eval Last

```text
先上线
出问题以后再想怎么测试
```

---

### No Recovery

```text
任务失败
唯一按钮：
[重试]
```

如果自己的系统大量符合这些特征，那大概率还没有真正完成 AI Native 改造。

---

## 二十一、把整个开发流程最后压缩成一张图

如果现在让我从头做一个 AI Native 软件，我会按照这样的顺序：

```text
1. 找一个真正有价值的 Goal
              ↓
2. 写 Goal Contract
目标 / 输入 / Done / 约束 / Evidence / Human Gate
              ↓
3. 拆 Goal Tree
              ↓
4. 映射需要的能力
Context / Skill / Tool / State / Artifact / Verifier
              ↓
5. 做最小垂直闭环
一个 Agent + 少量 Tool
              ↓
6. 设计 Agent Environment
可读 / 可做 / 可验 / 可续 / 有界
              ↓
7. 建立持久 State 和 Artifact
              ↓
8. 建立 Guardrail 和 Human Gate
              ↓
9. 建立 Verifier 和 Eval
              ↓
10. 再设计 UI
Intent / Progress / Artifact / Intervention
              ↓
11. 用真实任务持续测试
              ↓
12. 达到质量以后再优化模型和成本
              ↓
13. 通过 Release Gate
              ↓
14. Canary 小范围上线
              ↓
15. Trace 生产失败
              ↓
16. 把失败变成 Tool / Skill /
Context / Verifier / Guardrail + Eval
              ↓
17. 第二个 Goal
              ↓
18. 真正出现复用以后再平台化
```

这其实就是整个 AI Native 开发方法最核心的一条线。

---

## 二十二、所以 AI Native 软件开发真正改变的，不只是“用了 AI”

传统软件开发，我们经常先问：

> **“这个系统要有哪些功能？”**

然后设计：

```text
页面
按钮
接口
数据库
```

AI Native 开发则需要先问：

> **“用户最终想完成什么？”**

再往下推：

```text
为了完成它，
Agent 要知道什么？
↓
需要什么专业方法？
↓
需要调用什么能力？
↓
哪些事实必须被系统保存？
↓
什么事情不能让模型决定？
↓
怎样证明真的完成？
↓
失败以后怎么继续？
↓
用户什么时候需要介入？
```

然后这些问题才逐渐长成：

```text
Context
Skill
Tool
State
Guardrail
Verifier
Artifact
UI
```

所以 AI Native 并不是：

> **把传统软件扔掉，全部换成大模型。**

也不是：

> **Prompt 写得特别复杂。**

更不是：

> **搞一群 Agent 自己聊天。**

真正的变化是：

> **我们第一次开始围绕“让系统自己完成一个用户目标”，重新组织整个软件。**

模型只是负责其中最适合它的那一块：

> **处理模糊性、做判断。**

代码继续负责：

> **守住事实、状态、权限和确定性。**

Harness负责：

> **让工作持续运行。**

Environment负责：

> **提供真实可操作的工作世界。**

Skill负责：

> **提供专业方法。**

Tool负责：

> **真的行动。**

Verifier负责：

> **证明事情做完了。**

人则从过去的：

> **软件流程操作员**

逐渐上移成：

> **目标提出者、约束制定者、关键决策者和最终成果验收者。**

到这里，一个 AI Native 软件才真正从：

> **“传统软件里多了一点 AI”**

走到了：

> **“整个软件开始围绕用户目标重新组织。”**

而这，才是我理解的：

**AI Native 软件开发。**
